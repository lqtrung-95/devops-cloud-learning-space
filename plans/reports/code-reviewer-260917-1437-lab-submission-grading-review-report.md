## Bug found and fixed

**Empty/whitespace content silently completes an evidence-only lab.** `gradeLabSubmission` (`lab-submission-grader.ts:100-109`) returns `{passed:false, autoGraded:false, outcomes:[]}` whenever `spec.checks.length === 0` — **regardless of `content`**. `submitLabAction`'s completion branch is `if (grade.passed || !grade.autoGraded)` (`:118`), so for any lab with `checks: []` ("evidence-only", the plan's own "escape hatch" for hard-to-check labs, intended for phase 05), a direct call with `content: ""` marks the lab done and stores an empty evidence row. The client UI already disables submit on empty content (`lab-submission-panel.tsx:42`), but the server action itself (`submitLabSchema`, `learning-progress-actions.ts:81-85`) had no `min` bound — only `max(LAB_SUBMISSION_MAX_LENGTH)`. Not exploitable today (M04's 4 labs all have `checks.length > 0`, so `autoGraded` is always `true` and this branch is unreachable for the shipped content) but it's a real gap in the general `submitLabAction` logic that phase 05 will hit as soon as one evidence-only lab exists, and it's a stronger cheat than the plan's explicitly-accepted "learner types the expected string" risk (that risk assumes *some* effort; this needs zero).

Fixed: `content: z.string().max(LAB_SUBMISSION_MAX_LENGTH)` → `content: z.string().trim().min(1).max(LAB_SUBMISSION_MAX_LENGTH)` in `submitLabSchema` (`src/app/actions/learning-progress-actions.ts:81-85`). Re-ran `pnpm typecheck && pnpm lint && pnpm test` — all clean (109/109 tests). This also has the side benefit of storing trimmed content rather than raw whitespace-padded pastes.

## Matcher engine review (`lab-submission-grader.ts`, 109 lines)

- **Regex flag allowlist**: `ALLOWED_REGEX_FLAGS = /^[ims]*$/` (`:10`), checked in `compileRegex` before `new RegExp(...)` (`:36-43`). Correctly rejects `g`/`d`/`u`/`y`/`v` and any mix containing a disallowed flag (empirically re-verified via the tester's added test cases and my own read of the regex). `g` specifically is the right one to block — a stateful `lastIndex` on a reused/shared RegExp would be a real correctness bug if this were ever memoized, though as written a fresh `RegExp` is constructed per call so `g` wouldn't currently misbehave — the allowlist is still the right call for author ergonomics (least-surprise) and matches the plan.
- **10KB truncation**: `content.slice(0, LAB_SUBMISSION_MAX_LENGTH)` (`:101`) happens once, before any matcher runs, and before the `checks.length === 0` early return — order is right (early return is a separate branch, truncation cost is trivial either way). Verified boundary behavior via the tester's added at-boundary test — correct.
- **`numberInRange`**: capture group 1 via `Number.parseFloat`, `NaN` short-circuits to fail before min/max are applied (`:56-57`) — correct, no `min`/`max` bypass on non-numeric input. Flags are hardcoded to `undefined` for this matcher (`:52`), matching the type (`LabCheckMatcher` gives `numberInRange` no `flags` field) — intentional, not an oversight.
- **`jsonHasKeys`**: `JSON.parse` in try/catch, dot-path walker (`hasDotPath`, `:64-71`) correctly fails on any non-object hop and on `undefined` leaves; a `null` leaf is treated as "present" (documented behavior, matches the tester's added test) — reasonable, since `null` is a valid, present JSON value; only genuinely-missing keys should fail.
- **Total-function guarantee**: every matcher path returns `boolean`, never throws — confirmed by inspection (all `try/catch` boundaries are per-matcher, `runCheck`'s switch has no default-throw path since `LabCheckMatcher` is a closed union and TS exhaustiveness would catch a missing case at compile time).
- **Residual ReDoS risk** (informational, not blocking pilot): author-supplied `pattern` in `regex`/`numberInRange` is compiled and run against learner-controlled content with no execution timeout and no catastrophic-backtracking static check (the validator only confirms the pattern *compiles*, `module-definition-validator.ts:143-149`). Truncation to 10k chars limits blast radius but does not eliminate it — a genuinely pathological pattern (e.g. nested quantifiers like `(a+)+$`) can hang well within a 10k-char budget. Not a problem today: I checked all 5 regex patterns actually shipped in M04 (`uid=(?!0\b)\d+`, the two `^.*\bdb\b.*\(healthy\).*$`/redis variant, `EXIT_CODE=(\d+)`, `^sha256:[0-9a-f]{64}$`) and none has nested/ambiguous quantifiers — all are linear. Worth a note for phase 05 (more authors, more labs, no review gate) rather than a phase 01-04 blocker.
