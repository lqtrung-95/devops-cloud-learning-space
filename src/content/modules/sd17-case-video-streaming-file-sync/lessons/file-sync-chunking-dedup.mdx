Đây là ý tưởng cốt lõi đứng sau **content-defined chunking (CDC)** — kỹ thuật Dropbox và nhiều hệ thống sync/backup dùng để chia file thành các khối (chunk) sao cho một chỉnh sửa nhỏ chỉ ảnh hưởng vài chunk lân cận, thay vì làm hỏng dedup của toàn bộ phần còn lại của file.

<Technical>

### 1. Requirements (Dropbox-like)

**Functional**
- Người dùng có 1 thư mục đồng bộ trên nhiều thiết bị; sửa file ở một thiết bị, các thiết bị khác nhận được thay đổi.
- Chỉ truyền phần dữ liệu đã đổi (delta sync), không truyền lại nguyên file mỗi lần sửa.
- Không lưu trùng lặp nội dung giống hệt nhau nhiều lần (dedup) — kể cả giữa các version của cùng 1 file.

**Non-functional**
- Băng thông là tài nguyên quý (nhiều người dùng mạng di động/giới hạn) — ưu tiên truyền ít nhất có thể.
- Storage cần hiệu quả ở quy mô hàng trăm triệu file × nhiều version.
- Đồng bộ không cần real-time tuyệt đối nhưng cần "nhanh cảm nhận được" (vài giây tới vài chục giây).

### 2. Ước lượng (giả định minh hoạ)

| Đại lượng | Giả định | Kết quả |
|---|---|---|
| Người dùng | 10 triệu user, trung bình 2GB dữ liệu/user | 20 PB dữ liệu logic (chưa tính dedup/version) |
| Tần suất sửa | Trung bình 20 lần sửa file/ngày/user, mỗi lần đổi ~1% dung lượng file đó | Nếu chunk theo nội dung, lượng dữ liệu cần truyền lại mỗi lần sửa ~ vài chunk (KB) thay vì cả file |
| Hiệu quả dedup | Nhiều file người dùng khác nhau trùng nội dung (ảnh mẫu, template, thư viện) | Dedup toàn cục theo hash chunk có thể giảm đáng kể storage thật — tỉ lệ cụ thể tuỳ dữ liệu, **cần đo trên tập dữ liệu thật**, không giả định một con số cố định |

### 3. API & data model (rút gọn)

```http
POST /files/{id}/versions        # client gửi danh sách hash chunk của version mới
                                  # -> server trả về hash nào ĐÃ CÓ (không cần upload) và hash nào CẦN upload
PUT  /chunks/{hash}               # upload đúng những chunk server báo thiếu
POST /files/{id}/versions/{v}/commit   # xác nhận version mới đã đủ chunk, server ghi nhận version
```

```sql title="schema rút gọn"
CREATE TABLE files (
  id UUID PRIMARY KEY,
  owner_id UUID,
  path TEXT,
  latest_version INT
);

CREATE TABLE file_versions (
  file_id UUID REFERENCES files(id),
  version INT,
  chunk_hashes TEXT[],        -- danh sách hash chunk theo đúng thứ tự tạo nên file ở version này
  created_at TIMESTAMPTZ,
  PRIMARY KEY (file_id, version)
);

CREATE TABLE chunks (
  hash TEXT PRIMARY KEY,      -- ví dụ SHA-256 của nội dung chunk
  size_bytes INT,
  object_key TEXT,            -- vị trí lưu thật trong object storage
  ref_count BIGINT DEFAULT 1  -- bao nhiêu version/file đang tham chiếu chunk này — dùng khi cần dọn rác
);
```

Điểm quan trọng của thiết kế này: `chunks` là bảng **toàn cục**, không thuộc riêng file nào. Hai file khác nhau (thậm chí của hai user khác nhau, nếu hệ thống dedup toàn cục) chứa cùng một đoạn nội dung sẽ **trỏ chung một hàng `chunks`** — đây chính là dedup.

### 4. Content-defined chunking hoạt động thế nào

Thay vì cắt theo vị trí byte cố định, CDC trượt một **cửa sổ nhỏ** (ví dụ 48 byte) qua dữ liệu và tính một **rolling hash** của cửa sổ đó tại mỗi vị trí. Khi rolling hash thoả một điều kiện hiếm gặp (ví dụ N bit thấp đều bằng 0), vị trí đó được chọn làm **ranh giới chunk**. Vì rolling hash chỉ phụ thuộc vào 48 byte cục bộ (nội dung), không phụ thuộc offset tuyệt đối trong file, nên:

- Ranh giới "bám" theo nội dung xung quanh nó.
- Chèn/xoá dữ liệu ở một chỗ chỉ làm thay đổi ranh giới của (các) chunk chứa chỗ sửa đó — mọi ranh giới ở xa vẫn rơi đúng vị trí cũ (vì nội dung ở đó không đổi).
- Thường giới hạn thêm **kích thước tối thiểu/tối đa** cho mỗi chunk (ví dụ 2KB–64KB) để tránh chunk quá nhỏ (overhead metadata) hoặc quá lớn (mất lợi ích dedup khi có sửa đổi).

```ts title="cdc-chunker.ts (rút gọn, minh hoạ ý tưởng — không phải cài đặt Rabin fingerprint đầy đủ)"
import { createHash } from "node:crypto";

interface Chunk { hash: string; length: number }

function cdcChunk(buffer: Buffer, opts: { min: number; max: number; windowSize: number; maskBits: number }): Chunk[] {
  const chunks: Chunk[] = [];
  let start = 0;
  for (let i = opts.windowSize; i < buffer.length; i++) {
    const sinceStart = i - start;
    const window = buffer.subarray(i - opts.windowSize, i);
    const rollingValue = simpleRollingHash(window); // thay bằng Rabin fingerprint thật trong hệ thống production
    const isBoundary = (rollingValue & ((1 << opts.maskBits) - 1)) === 0;
    if ((isBoundary && sinceStart >= opts.min) || sinceStart >= opts.max) {
      chunks.push({ hash: sha256(buffer.subarray(start, i)), length: i - start });
      start = i;
    }
  }
  chunks.push({ hash: sha256(buffer.subarray(start)), length: buffer.length - start });
  return chunks;
}

function sha256(data: Buffer): string {
  return createHash("sha256").update(data).digest("hex");
}
```

| Cách chia chunk | Ưu | Nhược | Dùng khi |
|---|---|---|---|
| Fixed-size (offset cố định) | Cực đơn giản, tốc độ chia nhanh nhất | Chèn/xoá dữ liệu làm lệch mọi ranh giới phía sau — dedup/delta sync gần như vô dụng sau điểm sửa | File không bao giờ chèn/xoá giữa chừng, chỉ append hoặc ghi đè toàn bộ (ví dụ log file chỉ append) |
| Content-defined (rolling hash) | Chèn/xoá chỉ ảnh hưởng chunk lân cận — dedup/delta sync hiệu quả với mọi kiểu sửa | Tính rolling hash tốn CPU hơn, kích thước chunk không đều (cần giới hạn min/max) | File người dùng chỉnh sửa tuỳ ý (document, code, ảnh đã chỉnh) — đúng use case của Dropbox |

**Khi nào đổi ý:** nếu dữ liệu chỉ ghi theo kiểu append-only (ví dụ log, backup tăng dần), fixed-size đã đủ tốt và đơn giản hơn nhiều — CDC chỉ đáng giá thêm phức tạp khi chỉnh sửa có thể xảy ra ở giữa file.

</Technical>

<Callout type="mistake" title="Quên đặt min/max size cho content-defined chunking">
  Không giới hạn kích thước, rolling hash có thể (hiếm nhưng có thể) tạo ra chunk cực nhỏ (vài byte, tốn overhead lưu hash/metadata cho mỗi chunk) hoặc cực lớn (nếu lâu không gặp điều kiện boundary, mất luôn lợi ích dedup cho cả đoạn dài đó). Luôn đặt `min`/`max` rõ ràng và cắt cứng khi chạm `max`.
</Callout>

<Callout type="info" title="Góc phỏng vấn">
  Câu hỏi kinh điển: "vì sao Dropbox không chỉ diff toàn bộ file như `git diff`?" — điểm mấu chốt để trả lời tốt: diff dạng text (byte-by-byte, kiểu Myers diff) tốn CPU tuyến tính theo kích thước file mỗi lần so sánh và không tận dụng được dedup TOÀN CỤC giữa nhiều file/user khác nhau. Chunking theo nội dung cho phép so sánh bằng hash (rẻ hơn nhiều) và dedup vượt ra ngoài phạm vi một file.
</Callout>
