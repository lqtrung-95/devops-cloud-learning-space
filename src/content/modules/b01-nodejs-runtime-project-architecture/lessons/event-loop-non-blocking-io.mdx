  Tưởng tượng một quán cà phê chỉ có **một pha chế**. Khách A gọi espresso — pha chế bấm nút máy pha (việc chậm), rồi **không đứng đó chờ** mà quay lại nhận order của khách B ngay. Khi máy pha xong, nó "kêu bíp" và pha chế quay lại lấy ly cà phê giao cho khách A.

  Pha chế đó chính là **luồng chính (main thread)** của Node.js. Máy pha espresso là các việc I/O chậm (đọc file, gọi database, gọi HTTP). **Event loop** là cách pha chế quyết định: "giờ tới lượt việc gì được làm tiếp?".

  Điểm khác: pha chế còn có một cuốn sổ ưu tiên riêng (`process.nextTick`) — việc ghi vào đó luôn được xử lý trước cả những việc "khách quen đã hẹn trước" (Promise).
</Eli5>

<Technical>

### Một luồng, không chặn (single-threaded, non-blocking)

Node.js chạy JavaScript của bạn trên **một luồng chính duy nhất**. Không có threads song song cho code của bạn như Java hay Go. Vậy vì sao Node vẫn xử lý được hàng ngàn request cùng lúc?

Vì các việc **I/O chậm** (đọc file, query Postgres, gọi Redis, gọi API khác) không được thực hiện trực tiếp trên luồng chính — chúng được giao cho **libuv** (thư viện C bên dưới Node), thứ có một **thread pool** riêng và dùng các cơ chế bất đồng bộ của hệ điều hành. Luồng chính chỉ đăng ký "khi nào xong thì gọi lại callback này", rồi rảnh tay làm việc khác ngay.

### Call stack — nơi code đang chạy

**Call stack** là nơi JavaScript engine (V8) thực thi code đồng bộ, theo kiểu ngăn xếp (LIFO — vào sau ra trước). Khi bạn gọi một hàm, nó được đẩy lên đỉnh stack; hàm chạy xong thì bị lấy ra.

Event loop chỉ được phép chuyển sang bước tiếp theo (xử lý queue nào đó) khi **call stack hoàn toàn rỗng**.

### Ba loại "hàng đợi" callback

| Hàng đợi | Ví dụ | Khi nào được xử lý |
|---|---|---|
| `process.nextTick` queue | `process.nextTick(fn)` | Ngay sau khi call stack rỗng, **trước cả** microtask — đặc thù riêng của Node |
| Microtask queue | `Promise.then/catch/finally`, `queueMicrotask` | Sau khi nextTick queue rỗng, **trước** khi sang macrotask tiếp theo |
| Macrotask queue (theo phase) | `setTimeout`, `setInterval`, I/O callback, `setImmediate` | Từng phase một của event loop (Timers → Pending callbacks → Poll → Check → Close) |

Quy tắc quan trọng nhất: **sau mỗi callback đơn lẻ nào chạy xong** (kể cả một macrotask), Node xả hết `nextTick` queue rồi tới microtask queue, trước khi tiếp tục bất cứ việc gì khác. Không phải chỉ "giữa các phase" mà là sau **mỗi tác vụ**.

### Ví dụ đã kiểm chứng từng bước

```ts title="scripts/event-loop-order.ts"
console.log("1: start");

setTimeout(() => console.log("2: setTimeout"), 0);

Promise.resolve().then(() => console.log("3: promise"));

process.nextTick(() => console.log("4: nextTick"));

console.log("5: end");
```

Lần theo từng bước: code đồng bộ chạy hết trước, in `1: start` rồi `5: end` (ba dòng ở giữa chỉ *đăng ký* callback, không chạy ngay). Call stack rỗng → Node xả `nextTick` queue: in `4: nextTick`. Xong nextTick, xả microtask queue: in `3: promise`. Cuối cùng, cả hai hàng đợi ưu tiên đã rỗng, event loop mới cho phép phase Timers chạy: in `2: setTimeout`.

**Output thật:** `1: start`, `5: end`, `4: nextTick`, `3: promise`, `2: setTimeout`.

</Technical>

<Callout type="mistake">
  Nghĩ rằng `setTimeout(fn, 0)` chạy "ngay lập tức". Nó chỉ được đăng ký vào macrotask queue — vẫn phải đợi call stack rỗng **và** cả `nextTick` lẫn microtask queue rỗng trước, nên trong ví dụ trên nó luôn chạy **cuối cùng**, dù được gọi đầu tiên trong 3 lệnh async.
</Callout>

<Callout type="warning" title="Đừng lạm dụng process.nextTick">
  Gọi `process.nextTick` đệ quy liên tục (tự gọi lại chính nó) sẽ khiến hàng đợi nextTick không bao giờ rỗng — event loop bị "đói" (starvation), không bao giờ tới được phase Timers hay xử lý I/O thật. Đây là lỗi thật đã từng làm treo cả server Node trong production.
</Callout>
