### CommonJS vs ESM

Node.js hỗ trợ 2 hệ thống module:

| | CommonJS (cũ) | ESM — ES Module (taskflow-api dùng cái này) |
|---|---|---|
| Cú pháp | `require()` / `module.exports` | `import` / `export` |
| Bật bằng | Mặc định nếu không khai báo gì | `"type": "module"` trong `package.json` |
| Import file tương đối | Không cần đuôi file | **Bắt buộc** ghi đuôi `.js` kể cả khi source là `.ts` |
| Top-level `await` | Không hỗ trợ | Hỗ trợ |

```json title="package.json"
{
  "name": "taskflow-api",
  "type": "module",
  "engines": { "node": ">=22" }
}
```

Vì taskflow-api viết bằng TypeScript nhưng chạy trên Node ESM thật, import file nội bộ phải ghi đuôi `.js` (đuôi của file **sau khi biên dịch**), dù file nguồn là `.ts`:

```ts title="src/app.ts"
import { registerHealthRoute } from "./routes/health.js"; // đúng — dù file thật là health.ts
```

### tsconfig.json cho backend Node 22

```json title="tsconfig.json"
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "moduleResolution": "NodeNext",
    "strict": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "outDir": "dist",
    "rootDir": "src"
  },
  "include": ["src"]
}
```

- `"strict": true` bật toàn bộ kiểm tra kiểu chặt (`strictNullChecks`, `noImplicitAny`...) — bắt lỗi lúc biên dịch thay vì lúc production.
- `"module"` và `"moduleResolution": "NodeNext"` làm TypeScript mô phỏng đúng cách Node.js thật sự resolve module ESM, bao gồm cả quy tắc bắt buộc đuôi `.js` ở trên.

### Cấu trúc thư mục theo layer

```
taskflow-api/
├── src/
│   ├── app.ts              # khởi tạo Fastify instance, đăng ký route/plugin
│   ├── config/
│   │   └── env.ts          # validate biến môi trường bằng Zod
│   ├── routes/
│   │   └── health.ts       # lớp HTTP — chỉ nhận request, gọi service, trả response
│   ├── services/
│   │   └── health-service.ts  # logic nghiệp vụ thật
│   ├── db/
│   │   └── client.ts       # kết nối Postgres (dùng thật từ B04)
│   └── plugins/            # Fastify plugin dùng chung (log, error handler...)
├── docker-compose.yml
├── Dockerfile
├── tsconfig.json
└── package.json
```

### Validate biến môi trường bằng Zod

Đừng tin `.env` một cách mù quáng — thiếu một biến môi trường lúc chạy production tệ hơn nhiều so với báo lỗi ngay lúc khởi động:

```ts title="src/config/env.ts"
import "dotenv/config";
import { z } from "zod";

const envSchema = z.object({
  PORT: z.coerce.number().int().positive().default(3000),
  DATABASE_URL: z.string().url(),
  REDIS_URL: z.string().url(),
});

// Ném lỗi và dừng process ngay nếu thiếu/sai biến — không để app chạy "nửa vời".
export const env = envSchema.parse(process.env);
```

Gọi `import { env } from "./config/env.js"` ở bất kỳ đâu cần `env.PORT`, `env.DATABASE_URL` — TypeScript biết chính xác kiểu dữ liệu, không còn `process.env.PORT` kiểu `string | undefined`.

<Callout type="mistake">
  Quên đuôi `.js` khi import file tương đối dưới cấu hình `NodeNext` (`import { env } from "./config/env"` — thiếu đuôi). TypeScript báo lỗi resolve module ngay lúc biên dịch, nhưng nhiều người tưởng nhầm là lỗi cấu hình khác.
</Callout>

<Callout type="warning" title="Đừng commit file .env">
  `.env` chứa `DATABASE_URL`/`REDIS_URL` (và sau này là secret thật) — luôn thêm vào `.gitignore` ngay từ commit đầu tiên. Dùng `.env.example` để ghi lại tên biến cần có, không kèm giá trị thật.
</Callout>
