<Eli5 title="Locking giống phòng thử đồ có chìa khoá và tài liệu có số phiên bản" emoji="🔐">

**Pessimistic locking** giống **phòng thử đồ có chìa khoá**: ai vào trước thì cầm chìa, khoá cửa lại; người sau đứng chờ ngoài cửa tới khi người trong trả chìa. Không bao giờ hai người cùng thay đồ trong một phòng — nhưng nếu người bên trong ngồi gọi điện nửa tiếng, cả hàng người phải chờ. Người đứng ngoài vẫn *nhìn* được tấm ảnh chụp phòng lúc trước; chỉ không được *vào sửa*.

**Optimistic locking** giống **sửa tài liệu có số phiên bản**: ai cũng lấy "bản số 7" về sửa thoải mái, không phải chờ ai. Lúc nộp, thư ký kiểm tra: "tài liệu vẫn đang là bản 7 chứ?" Nếu người khác đã nộp thành bản 8, bạn phải lấy bản 8 về sửa lại.

Chỗ ví von hụt: trong database, "người chờ ngoài cửa" có thể chờ nhau vòng tròn (deadlock) — database sẽ phát hiện và huỷ một người, còn phòng thử đồ thật thì không.

</Eli5>

"Trừ tiền", "giữ ghế", "trừ tồn kho" là những luồng mà sai một lần là mất tiền thật. Bài trước cho thấy READ COMMITTED mặc định không chặn lost update. Bài này là bộ công cụ thực tế để chặn nó — và cách chọn đúng công cụ theo **mức độ xung đột** và **thời gian giữ dữ liệu**.

<Technical>

### Bốn cách chống lost update

1. **Atomic update** — để database tự tính: `UPDATE accounts SET balance = balance - 50 WHERE id = 1 AND balance >= 50`. Kiểm tra `rowCount`: 0 ⇒ không đủ tiền. Đơn giản và nhanh nhất khi logic viết được bằng một câu SQL.
2. **Pessimistic lock** — `SELECT … FOR UPDATE`, xử lý trong app, rồi `UPDATE` trong cùng transaction.
3. **Optimistic lock** — version column (hoặc `updated_at`/ETag), ghi có điều kiện, retry khi thua.
4. **Isolation cao hơn** — REPEATABLE READ/SERIALIZABLE + retry `40001` (bài trước).

### `SELECT … FOR UPDATE` — semantics trong PostgreSQL

- Khoá **các dòng được trả về** tới hết transaction (COMMIT/ROLLBACK). Không có "unlock" giữa chừng.
- Transaction khác muốn `UPDATE`, `DELETE`, `SELECT … FOR UPDATE`/`FOR NO KEY UPDATE`/`FOR SHARE` các dòng đó sẽ **chờ**. `SELECT` thường **không** bị chặn (MVCC) và đọc phiên bản đã commit.
- Ở READ COMMITTED, khi hết chờ, câu lệnh kiểm tra lại điều kiện `WHERE` trên **phiên bản mới nhất** của dòng rồi mới trả kết quả. Ở REPEATABLE READ/SERIALIZABLE, nếu dòng đã bị sửa sau snapshot thì nhận lỗi `40001`.
- Biến thể hữu ích:
  - `FOR UPDATE NOWAIT` — không chờ, báo lỗi ngay nếu dòng đang bị khoá.
  - `FOR UPDATE SKIP LOCKED` — bỏ qua dòng đang bị khoá; hợp cho **job queue** nhiều worker lấy việc.
  - `FOR NO KEY UPDATE` — khoá nhẹ hơn khi không đổi khoá chính, ít đụng foreign key check hơn.
- **Không khoá được dòng chưa tồn tại.** "Kiểm tra chưa ai đặt rồi INSERT" vẫn hỏng — dùng `UNIQUE`/`EXCLUDE` constraint, SERIALIZABLE, hoặc khoá một dòng "cha" (vd dòng `rooms`).

```sql title="Pessimistic: rút 50 từ tài khoản 1"
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- app kiểm tra balance >= 50, gọi rule nghiệp vụ (KHÔNG gọi API chậm ở đây)
UPDATE accounts SET balance = balance - 50 WHERE id = 1;
INSERT INTO ledger (account_id, amount, idempotency_key) VALUES (1, -50, 'req-7f3a');
COMMIT;
```

### Deadlock & timeout

- T1 khoá tài khoản A rồi xin B; T2 khoá B rồi xin A ⇒ chờ vòng tròn. PostgreSQL kiểm tra sau `deadlock_timeout` (mặc định 1s) và huỷ một bên với SQLSTATE `40P01`.
- Phòng tránh: **luôn khoá theo thứ tự cố định** (vd `ORDER BY id` khi chuyển tiền giữa hai tài khoản), giữ transaction ngắn, đặt `lock_timeout` để không treo vô hạn.

### Optimistic locking

```ts title="app/src/accounts/withdraw-optimistic.ts"
import type { Pool } from "pg";

export async function withdraw(pool: Pool, accountId: number, amount: number, maxAttempts = 3): Promise<number> {
  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    const { rows } = await pool.query("SELECT balance, version FROM accounts WHERE id = $1", [accountId]);
    if (rows.length === 0) throw new Error("account not found");
    const { balance, version } = rows[0] as { balance: number; version: number };
    if (balance < amount) throw new Error("insufficient funds");

    const result = await pool.query(
      "UPDATE accounts SET balance = $1, version = version + 1 WHERE id = $2 AND version = $3",
      [balance - amount, accountId, version],
    );
    if (result.rowCount === 1) return balance - amount;
    // Someone else wrote first: back off with jitter, then re-read and try again.
    await new Promise((resolve) => setTimeout(resolve, Math.random() * 10 * 2 ** attempt));
  }
  throw new Error("conflict: too many concurrent updates, try again");
}
```

Cùng ý tưởng xuất hiện ở khắp nơi: HTTP `ETag` + `If-Match` (trả `412 Precondition Failed`), DynamoDB `ConditionExpression`, Kubernetes `resourceVersion`.

### Chọn gì cho luồng trừ tiền?

- Logic viết được bằng một câu SQL ⇒ **atomic conditional update** ở READ COMMITTED + `CHECK (balance >= 0)` làm lưới an toàn.
- Cần đọc lên app để áp nhiều rule (hạn mức ngày, trạng thái KYC…) nhưng xử lý nhanh ⇒ **transaction ngắn + `FOR UPDATE`**, khoá theo thứ tự id.
- Xung đột hiếm, thời gian từ lúc đọc tới lúc ghi dài (form, workflow nhiều bước) ⇒ **optimistic**.
- Mọi phương án đều cần **idempotency key** để retry từ client không trừ tiền hai lần.

### Trade-off

| Lựa chọn | Ưu | Nhược | Dùng khi |
|---|---|---|---|
| Atomic conditional update | Không lock chủ động lâu, không retry, nhanh | Chỉ khi logic gói được trong một câu SQL | Trừ số dư, trừ tồn kho, tăng counter |
| Pessimistic (`FOR UPDATE`) | Đúng ngay lần đầu, không retry; hợp khi xung đột thường xuyên | Chờ lock làm giảm throughput; deadlock; không giữ được qua thời gian user suy nghĩ | Transaction ngắn trên dòng nóng, xung đột nhiều |
| Optimistic (version) | Không chặn ai, không giữ connection/lock, hợp với HTTP/stateless | Xung đột nhiều ⇒ retry dồn dập, tốn công vô ích; phải viết code retry | Xung đột hiếm, đọc–ghi cách nhau lâu |
| SERIALIZABLE + retry | Không phải tự tìm chỗ cần khoá | Tỉ lệ huỷ tăng theo tải; phải retry cả transaction | Bất biến phức tạp trải nhiều dòng |

**Khi nào đổi ý:** đo tỉ lệ `UPDATE 0` (optimistic) hoặc thời gian chờ lock (pessimistic). Retry vượt vài phần trăm request ⇒ nghiêng về pessimistic; lock wait chiếm phần lớn latency ⇒ thu nhỏ transaction hoặc chuyển optimistic/atomic.

</Technical>

<Callout type="mistake">

**Giữ `FOR UPDATE` trong khi gọi payment gateway hoặc chờ user xác nhận.** Mỗi request chiếm một connection và một row lock trong vài giây ⇒ pool cạn, request khác chờ dây chuyền. Tách thành: giữ chỗ (trạng thái `PENDING`) trong transaction ngắn → gọi bên ngoài → cập nhật kết quả trong transaction ngắn khác.

</Callout>

<Callout type="warning">

Optimistic locking mà **quên tăng `version`** hoặc **quên kiểm tra `rowCount`** thì không khác gì không khoá. Viết test concurrency (k6 nhiều VU cùng rút tiền) và so tổng tiền trước/sau — đừng chỉ đọc code.

</Callout>

<Callout type="info" title="Góc phỏng vấn">

Với câu "thiết kế ví/booking chống double-spend", một câu trả lời mạnh: chọn **atomic conditional update** hoặc **`FOR UPDATE` trong transaction ngắn** cho luồng trừ tiền, giải thích vì sao không optimistic (xung đột có thể cao ở tài khoản nóng), nhắc **khoá theo thứ tự** để tránh deadlock, **idempotency key** cho retry, và **constraint** (`CHECK balance >= 0`, `UNIQUE`) làm lưới an toàn. Nói thêm lock chỉ có tác dụng trong **một database** — khi dữ liệu nằm ở nhiều service thì phải dùng saga/outbox (SD07, SD12).

</Callout>
