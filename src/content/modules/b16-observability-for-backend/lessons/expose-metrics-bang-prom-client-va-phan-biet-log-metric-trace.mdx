Hai bài trước đã lo phần **log**: `requestId` bám theo mọi dòng log, xuyên cả `api` lẫn `notification-service`. Bài này thêm phần **metric** (`/metrics` bằng `prom-client`), rồi dùng đúng những gì đã xây để chứng minh giá trị thật của `requestId`: từ 1 lỗi 500, lần ra root cause chỉ bằng grep.

### `prom-client`: Registry, Counter, Histogram

```ts title="src/plugins/metrics.ts (mới ở B16)"
import client from "prom-client";
import fp from "fastify-plugin";
import type { FastifyInstance } from "fastify";

export const register = new client.Registry();

// Đếm tổng số request, phân theo method/route/status_code.
export const httpRequestsTotal = new client.Counter({
  name: "http_requests_total",
  help: "Tổng số HTTP request đã xử lý",
  labelNames: ["method", "route", "status_code"],
  registers: [register],
});

// Phân phối latency theo bucket — đủ để tính p50/p95/p99 sau này bằng PromQL.
export const httpRequestDurationSeconds = new client.Histogram({
  name: "http_request_duration_seconds",
  help: "Thời gian xử lý 1 HTTP request (giây)",
  labelNames: ["method", "route", "status_code"],
  buckets: [0.01, 0.05, 0.1, 0.3, 0.5, 1, 2, 5],
  registers: [register],
});

async function metricsPlugin(fastify: FastifyInstance) {
  fastify.get("/metrics", async (_request, reply) => {
    reply.header("Content-Type", register.contentType);
    return register.metrics();
  });
}

export const metricsRoute = fp(metricsPlugin);
```

### Ghi nhận số liệu ở đúng chỗ đã có sẵn: `onResponse`

`src/plugins/request-logger.ts` (B02, đã thêm `requestId` ở bài 1) đã có hook `onResponse` chạy sau MỌI request. Đây đúng là chỗ để cộng dồn metric — không cần thêm hook mới:

```ts title="src/plugins/request-logger.ts (cập nhật thêm ở B16)"
import { httpRequestDurationSeconds, httpRequestsTotal } from "./metrics.js";
// ... phần onRequest giữ nguyên như bài 1 ...

fastify.addHook("onResponse", async (request, reply) => {
  const durationMs = request.startTime ? Number(process.hrtime.bigint() - request.startTime) / 1_000_000 : undefined;
  request.log.info({ method: request.method, url: request.url, statusCode: reply.statusCode, durationMs }, "request completed");

  // MỚI ở B16: route lấy từ ROUTE PATTERN, không phải URL thô.
  const route = request.routeOptions.url ?? "unknown";
  const labels = { method: request.method, route, status_code: String(reply.statusCode) };
  httpRequestsTotal.inc(labels);
  if (durationMs !== undefined) httpRequestDurationSeconds.observe(labels, durationMs / 1000);
});
```

### Bẫy cardinality — vì sao KHÔNG dùng `request.url`

| Cách lấy label `route` | Số time series khi có 10.000 task | Vấn đề |
|---|---|---|
| `request.url` (thô, có ID thật: `/api/v1/tasks/3f2a-...`) | Tăng theo SỐ TASK thực tế — có thể tới hàng chục nghìn | Cardinality explosion: Prometheus tốn bộ nhớ lưu time series, chậm dần, có thể sập |
| `request.routeOptions.url` (mẫu route: `/api/v1/tasks/:id`) | Cố định theo SỐ ROUTE khai báo trong code | An toàn — đúng tinh thần "label phải có tập giá trị giới hạn" |

Đây là lỗi rất dễ mắc và rất tốn kém khi phát hiện muộn — luôn kiểm tra 1 label có tập giá trị HỮU HẠN trước khi gắn nó vào metric.

### Log, metric, trace — ba vai trò không được lẫn lộn

| Công cụ | Trả lời câu hỏi | Ví dụ cụ thể ở `taskflow-api` |
|---|---|---|
| **Log** (`requestId`, 2 bài trước) | Chuyện gì xảy ra ở ĐÚNG 1 request này? | Khách báo lỗi kèm `requestId` → grep đúng dòng log ở cả `api` và `notification-service` |
| **Metric** (`/metrics`, bài này) | Hệ thống có ổn không, nhìn TỔNG THỂ theo thời gian? | p95 latency của `/api/v1/tasks` trong 1 giờ qua có tăng bất thường không |
| **Distributed trace** (chưa triển khai ở module này) | Với 1 request cụ thể đi qua nhiều service, THỜI GIAN cụ thể tiêu tốn ở đâu? | Trong 1 lần gọi `resend`, mất bao lâu ở `api`, bao lâu ở mạng, bao lâu ở `notification-service` |

Ba công cụ này **bổ sung cho nhau, không thay thế nhau**: metric cho biết "có gì đó sai" (p95 tăng đột biến), log (nhờ `requestId`) cho biết "chính xác request nào và điều gì đã xảy ra", còn distributed tracing — bước tự nhiên tiếp theo, ví dụ dùng OpenTelemetry, ngoài phạm vi triển khai đầy đủ của module này — sẽ trả lời "thời gian trong request đó đi đâu" khi bức tranh có nhiều hơn 2 service. Nhầm vai trò của 3 công cụ (ví dụ cố dùng log để trả lời câu hỏi tổng thể của metric) khiến bạn tốn công đọc hàng nghìn dòng thay vì nhìn 1 con số.

</Technical>

### Lần dấu một lỗi 500 thật, chỉ bằng đúng 1 `requestId`

Bây giờ mọi mảnh ghép đã có đủ: `requestId` xuyên 2 process (bài 1, 2), `/metrics` để biết "có vấn đề" ở tầm hệ thống, và log để biết "vấn đề gì, ở request nào". Kịch bản dưới đây cố tình tạo ra một lỗi thật — không giả lập — để chứng minh giá trị của toàn bộ 2 bài trước.

<Trace500ErrorAcrossProcessesDiagram />

Root cause ở đây không nằm ở gRPC hay ở logic `api` — nó nằm ở DỮ LIỆU: một `notification` cũ mang giá trị `type` mà `notification-service` chưa từng được dạy để hiểu. Không có `requestId` xuyên 2 process, log `api` chỉ nói được "có lỗi 500, không rõ vì sao"; phải có đúng dòng log tương ứng bên `notification-service` mới thấy được lý do thật.

<Callout type="tip" title="Quy trình debug 1 lỗi 500 khi có ≥2 process">
  1. Lấy `requestId` từ header `x-request-id` của response lỗi (hoặc từ báo cáo của khách hàng).
  2. `docker compose logs <mọi service liên quan> | grep <requestId>` — một lệnh, không cần đoán service nào liên quan.
  3. Đọc log theo đúng thứ tự thời gian — dòng lỗi ở service NÀO xuất hiện ĐẦU TIÊN thường là nơi root cause thật sự nằm.
</Callout>

<Callout type="mistake">
  Cố dùng `/metrics` để tìm nguyên nhân của MỘT lỗi 500 cụ thể — metric không lưu chi tiết từng request, chỉ có số liệu tổng hợp. `/metrics` chỉ nên dùng để phát hiện "có bất thường" (ví dụ tỉ lệ lỗi 500 tăng), sau đó chuyển sang log (có `requestId`) để tìm chính xác request nào và vì sao.
</Callout>
