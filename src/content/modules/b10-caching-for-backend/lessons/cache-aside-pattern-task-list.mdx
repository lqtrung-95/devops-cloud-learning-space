Từ B04, mỗi lần gọi endpoint này là một lượt round-trip tới Postgres — kể cả khi 10 người đang mở cùng một board và không ai vừa đổi gì. ### Cache-aside là gì

Cache-aside (hay "lazy loading") là pattern đơn giản nhất: **ứng dụng** (không phải Redis) chịu trách nhiệm đọc/ghi cache, theo đúng 4 bước:

1. Nhận request đọc → build cache key từ tham số request
2. Hỏi Redis (`GET key`) — có (**HIT**) thì trả luôn, xong
3. Không có (**MISS**) → query Postgres như bình thường
4. Lưu kết quả vào Redis (`SET key value EX ttl`) trước khi trả response, để lần sau HIT

Điểm quan trọng: Redis không tự động biết phải chứa gì — nó chỉ là một cái kho lưu trữ key-value thụ động. Toàn bộ logic "khi nào đọc, khi nào ghi" nằm trong code route handler.

### Áp dụng cho GET /api/v1/projects/:projectId/tasks

```typescript title="src/lib/redis-client.ts"
import Redis from "ioredis";

// Cùng REDIS_URL đã có từ B01 (ioredis cũng là driver BullMQ dùng ở B09)
export const redis = new Redis(process.env.REDIS_URL ?? "redis://redis:6379");
```

```typescript title="src/lib/task-list-cache-key.ts"
interface TaskListCacheKeyParams {
  status?: string;
  cursor?: string;
  limit: number;
}

export function buildTaskListCacheKey(projectId: string, { status, cursor, limit }: TaskListCacheKeyParams): string {
  return `tasks:${projectId}:list:status=${status ?? "all"}:cursor=${cursor ?? "first"}:limit=${limit}`;
}

export function taskListRegistryKey(projectId: string): string {
  return `tasks:${projectId}:list:keys`;
}
```

```typescript title="src/routes/tasks.route.ts"
import { redis } from "../lib/redis-client";
import { buildTaskListCacheKey, taskListRegistryKey } from "../lib/task-list-cache-key";

const TASK_LIST_TTL_SECONDS = 30;

fastify.get(
  "/api/v1/projects/:projectId/tasks",
  { schema: { params: projectParamsSchema, querystring: listTasksQuerySchema } },
  async (request) => {
    const { projectId } = request.params;
    const { status, cursor, limit } = request.query;
    const cacheKey = buildTaskListCacheKey(projectId, { status, cursor, limit });

    const cached = await redis.get(cacheKey);
    if (cached) {
      return JSON.parse(cached);
    }

    const result = await queryTaskListFromPostgres(projectId, { status, cursor, limit }); // hàm Drizzle đã có từ B04

    await redis.set(cacheKey, JSON.stringify(result), "EX", TASK_LIST_TTL_SECONDS);
    await redis.sadd(taskListRegistryKey(projectId), cacheKey);

    return result;
  },
);
```

`redis.sadd` ghi thêm `cacheKey` vào một Redis Set riêng cho project đó — registry này không phục vụ việc đọc, chỉ để bài sau (invalidation) biết chính xác cần xoá key nào mà không phải quét (`KEYS`) toàn bộ keyspace.

### TTL 30 giây: lưới an toàn, không phải giải pháp chính

TTL 30 giây có nghĩa là dù invalidation ở bài sau có lỡ bị bỏ sót ở đâu đó, cache tự "tự sửa" chậm nhất sau 30 giây. Chọn TTL là một đánh đổi:

| TTL | Ưu | Nhược |
|---|---|---|
| Rất ngắn (vài giây) | Dữ liệu cũ tồn tại rất ngắn kể cả khi quên invalidate | Hit rate thấp hơn, gần như luôn phải hỏi Postgres |
| 30 giây (chọn ở đây) | Hit rate cao cho board đang mở liên tục; đủ ngắn để không ai chờ quá lâu nếu có invalidation bị sót | Vẫn có cửa sổ 30s dữ liệu cũ NẾU không invalidate chủ động |
| Rất dài (phút/giờ) | Hit rate cực cao | Nếu quên invalidate, người dùng thấy sai trong thời gian dài — rủi ro lớn cho dữ liệu hay đổi như task list |

30 giây hợp lý cho endpoint đọc nhiều, ghi thỉnh thoảng như task list — nhưng **chỉ là lưới an toàn**. Bài tiếp theo mới là phần quan trọng: invalidate chủ động ngay khi có write, để không ai phải chờ hết TTL mới thấy dữ liệu đúng.

Chênh lệch 38ms → 6ms không phải phép màu: lần thứ hai chỉ mất một round-trip Redis (trong cùng mạng Docker), bỏ hẳn phần connection pool + planner + đọc index của Postgres.

<Callout type="mistake" title="Đừng đặt cache check ở hook chạy trước authorization">
  Fastify chạy hook theo thứ tự `onRequest` → ... → `preHandler` (nơi `resolveOrganizationContext` + `requireRole` của B06 chạy) → handler. Nếu vì muốn "tối ưu thêm" mà chuyển việc `redis.get` lên `onRequest` để trả sớm hơn, request sẽ nhận được cache HIT **trước khi** RBAC kịp kiểm tra user có thuộc project/organization đó hay không. Cache-aside trong bài này nằm trong route handler — luôn chạy SAU toàn bộ `preHandler` — và phải giữ nguyên vị trí đó.
</Callout>
