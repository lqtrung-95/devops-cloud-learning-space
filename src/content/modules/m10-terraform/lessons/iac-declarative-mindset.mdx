Tưởng tượng bạn xây nhà. Cách thứ nhất: đứng cạnh thợ và dặn từng câu — "xây thêm 1 bức tường", "đổ thêm 1 tầng". Nếu hôm sau bạn lỡ dặn lại y hệt, thợ sẽ xây **thêm** 1 tầng nữa. Đó là kiểu **imperative** (mệnh lệnh từng bước).

Cách thứ hai: đưa thợ **bản vẽ** "nhà 3 tầng, 2 phòng ngủ". Thợ nhìn căn nhà hiện tại, so với bản vẽ, thiếu gì thì xây bù, thừa gì thì phá bớt. Đưa bản vẽ 10 lần thì nhà vẫn 3 tầng. Đó là kiểu **declarative** (khai báo kết quả mong muốn) — cách Terraform làm việc.

Chỗ ví von bị "gãy": thợ thật tự nhìn được căn nhà, còn Terraform phải **ghi sổ** những gì nó đã xây (state) rồi hỏi AWS API để biết thực tế ra sao.

</Eli5>

Ở M07–M08 bạn đã dựng VPC, ALB, ASG, RDS bằng Console. Thử tưởng tượng làm lại y hệt cho `staging`, hoặc khôi phục sau khi ai đó xoá nhầm: hàng trăm cú click, không review được, không biết ai đổi gì. **Infrastructure as Code (IaC)** biến hạ tầng thành file text nằm trong Git — review bằng PR, tái tạo bằng một lệnh, có lịch sử thay đổi.

<Technical>

### Imperative vs declarative

| | Imperative (bash + AWS CLI, SDK) | Declarative (Terraform, CloudFormation) |
|---|---|---|
| Bạn viết | Các **bước** cần làm | **Trạng thái cuối** mong muốn |
| Chạy lại | Làm lại các bước → dễ tạo trùng | Tính diff → chỉ làm phần chênh lệch |
| Idempotent | Phải tự viết logic kiểm tra | Có sẵn |
| Xoá tài nguyên | Viết thêm script xoá | Bỏ khỏi code → plan hiện `-` |
| Thứ tự | Bạn tự sắp | Công cụ tự dựng dependency graph |

**Idempotent** = chạy 1 lần hay 100 lần đều ra cùng kết quả. Đây là tính chất quan trọng nhất của IaC.

### Terraform hoạt động thế nào (tóm tắt)

1. Bạn viết file `.tf` bằng ngôn ngữ **HCL**.
2. **Provider** (plugin, ví dụ `hashicorp/aws`) dịch mỗi `resource` thành lời gọi API.
3. **State** ghi lại tài nguyên thật tương ứng với từng block trong code.
4. `terraform plan` so **code ↔ state ↔ thực tế** và in ra diff; `terraform apply` thực hiện diff đó.

```hcl title="main.tf"
resource "aws_s3_bucket" "assets" {
  bucket = "shop-assets-dev-123456789012"

  tags = {
    Environment = "dev"
    ManagedBy   = "terraform"
  }
}
```

### Terraform và các "đối thủ"

| Công cụ | Ngôn ngữ | State ở đâu | Ghi chú |
|---|---|---|---|
| **Terraform** | HCL | File state (local/S3/HCP Terraform) | Đa cloud, hệ sinh thái provider lớn nhất |
| **OpenTofu** | HCL | Như Terraform | Fork mã nguồn mở của Terraform (Linux Foundation), lệnh `tofu` |
| **CloudFormation** | YAML/JSON | AWS tự quản lý | Chỉ AWS, không cần lo state |
| **AWS CDK** | TypeScript, Python… | Sinh ra CloudFormation | Dùng vòng lặp/class của ngôn ngữ lập trình |
| **Pulumi** | TypeScript, Go, Python… | Pulumi Cloud hoặc tự host | Đa cloud, code "thật" |

Năm 2023 HashiCorp đổi license Terraform sang BSL, cộng đồng tách ra **OpenTofu** (giấy phép MPL). Với người học, cú pháp và workflow gần như giống hệt — những gì học ở module này dùng được cho cả hai. Hai bên có tính năng mới khác nhau theo thời gian, nên kiểm tra tài liệu mới nhất khi chọn cho dự án.

### Terraform không làm gì

Terraform giỏi **tạo/sửa/xoá tài nguyên cloud** (provisioning). Cài package, sửa file config bên trong server là việc của **configuration management** (Ansible) hoặc **image** dựng sẵn (Packer, Docker) — bạn sẽ học ở M11.

</Technical>

<Callout type="mistake">

**"ClickOps" rồi mới viết Terraform sau.** Tạo tay trên Console "cho nhanh" rồi định bổ sung code sau thường dẫn tới hạ tầng không ai tái tạo được. Nếu buộc phải tạo tay (sự cố khẩn cấp), hãy `import` vào Terraform ngay sau đó — bài 6 sẽ hướng dẫn.

</Callout>

<Callout type="info" title="Terraform hay OpenTofu?">

Module này dùng lệnh `terraform`. Nếu công ty bạn dùng OpenTofu, thay `terraform` bằng `tofu` — file `.tf`, provider và workflow gần như giữ nguyên.

</Callout>
