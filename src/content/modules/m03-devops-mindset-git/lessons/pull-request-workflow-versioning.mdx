<Eli5 title="Pull Request & branch protection giống như quy trình duyệt bài trước khi lên báo" emoji="📰">
  Phóng viên viết bài xong **không được tự tay đưa lên trang nhất**. Bài phải qua **máy kiểm tra chính tả tự động** (CI), rồi **biên tập viên phụ trách chuyên mục** đọc duyệt (code review, CODEOWNERS). Toà soạn có **nội quy cứng**: bài chưa đủ chữ ký duyệt thì máy in từ chối in — kể cả tổng biên tập (branch protection).

  Mỗi bài có **tiêu đề theo mẫu** ("[Sửa lỗi] …", "[Tin mới] …") để cuối tuần toà soạn tự tổng hợp mục lục (conventional commits → changelog). Và mỗi số báo có **số phát hành** cho biết thay đổi lớn hay nhỏ (semantic versioning).

  Chỗ ví dụ gãy: quy trình này không để "làm khó" nhau — mục tiêu là **bắt lỗi sớm, chia sẻ kiến thức**, và vẫn phải **nhanh**. PR chờ duyệt 3 ngày cũng là một kiểu lãng phí.
</Eli5>

Đây là phần "sample app xuyên suốt" bắt đầu có **quy trình**: từ nay mọi thay đổi vào `main` của `sample-app` đều đi qua PR, CI và review. Bấm thử ba kịch bản bên dưới.

### Một PR tốt

- **Nhỏ** và làm **một việc**; tiêu đề theo Conventional Commits (vì squash merge sẽ dùng tiêu đề PR làm commit message).
- Mô tả: *vì sao* thay đổi, *cách test*, ảnh chụp/log nếu có, rủi ro & cách rollback.
- Reviewer tập trung vào logic, thiết kế, bảo mật; phần định dạng để **máy** lo (formatter, linter).

```markdown title=".github/pull_request_template.md"
## Vì sao?
<!-- Link issue, bối cảnh -->

## Thay đổi gì?

## Test thế nào?
- [ ] Unit test pass (`npm test`)
- [ ] Đã chạy local với docker compose

## Rủi ro / rollback
```

### Branch protection & CODEOWNERS

Trên GitHub: *Settings → Branches* (classic branch protection) hoặc *Settings → Rules → Rulesets* (cơ chế mới hơn, linh hoạt hơn). Với repo private, một số tính năng phụ thuộc gói GitHub — kiểm tra tài liệu hiện hành. Các rule nên bật cho `main`:

| Rule | Tác dụng |
|---|---|
| Require a pull request before merging | Không push thẳng |
| Require approvals (≥ 1) + Require review from Code Owners | Đúng người phụ trách phải duyệt |
| Dismiss stale approvals | Push commit mới thì approval cũ bị huỷ |
| Require status checks to pass (vd `test`) + branch up to date | CI đỏ thì không merge |
| Block force pushes, restrict deletions | Không ai viết lại lịch sử main |
| Do not allow bypassing / include administrators | Admin cũng theo quy trình |

```text title=".github/CODEOWNERS"
# Quy tắc khớp SAU CÙNG thắng
*                   @trung
/api/               @trung @org/backend-team
/infra/             @org/platform-team
/.github/workflows/ @org/platform-team
```

### Conventional Commits

Cấu trúc: `type(scope)!: mô tả` + body + footer.

| Type | Khi nào | Ảnh hưởng version |
|---|---|---|
| `feat` | Tính năng mới | MINOR |
| `fix` | Sửa lỗi | PATCH |
| `feat!` / footer `BREAKING CHANGE:` | Phá vỡ tương thích | MAJOR |
| `docs`, `chore`, `refactor`, `test`, `ci`, `build`, `perf`, `style` | Còn lại | Thường không release (tuỳ cấu hình công cụ) |

### Semantic Versioning `MAJOR.MINOR.PATCH`

<SemverBumpDiagram />

- **MAJOR**: thay đổi không tương thích ngược (xoá endpoint, đổi format response).
- **MINOR**: thêm tính năng, tương thích ngược. **PATCH**: sửa lỗi tương thích ngược.
- Pre-release: `2.0.0-rc.1`. Giai đoạn `0.y.z` được coi là chưa ổn định — API có thể đổi bất cứ lúc nào.
- Công cụ tự động hoá từ commit: **semantic-release**, **release-please** (tạo PR release + changelog).

### Pre-commit hooks — bắt lỗi trước cả khi commit

```yaml title=".pre-commit-config.yaml"
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0            # chạy `pre-commit autoupdate` để lấy bản mới nhất
    hooks:
      - id: trailing-whitespace
      - id: end-of-file-fixer
      - id: check-yaml
      - id: check-added-large-files
      - id: detect-private-key
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.21.2
    hooks:
      - id: gitleaks        # quét secret (API key, token) trong thay đổi
  - repo: https://github.com/compilerla/conventional-pre-commit
    rev: v3.6.0
    hooks:
      - id: conventional-pre-commit
        stages: [commit-msg]   # kiểm tra message theo Conventional Commits
```

Hook chạy trên máy dev nên **có thể bị bỏ qua** (`git commit --no-verify`). Vì vậy các kiểm tra quan trọng phải **chạy lại trong CI** — hook chỉ để phản hồi nhanh hơn.

Nếu dùng **Rulesets** thay vì branch protection cổ điển, thông báo lỗi sẽ khác (dạng `GH013: Repository rule violations found`) nhưng ý nghĩa tương tự.

<Callout type="mistake" title="Required status check không bao giờ chạy">
  Bạn bắt buộc check tên `test`, nhưng workflow CI đặt tên job là `unit-tests` → PR treo mãi ở "Expected — Waiting for status to be reported". Tên check trong rule phải **khớp chính xác** tên job hiển thị trên PR.
</Callout>

<Callout type="warning" title="Bump MAJOR âm thầm">
  Đổi format JSON response hoặc xoá field mà commit là `fix:` → công cụ release chỉ tăng PATCH, client tự động cập nhật và… vỡ. Thay đổi phá vỡ tương thích **phải** đánh dấu `!` hoặc `BREAKING CHANGE:`.
</Callout>
