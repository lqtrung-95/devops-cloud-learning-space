### Repeatable job: lịch sống trong Redis, không phải trong RAM

BullMQ hỗ trợ thêm một job "lặp lại" theo lịch cron hoặc theo chu kỳ cố định khi `add()`:

```ts title="src/queues/cleanup-queue.ts"
import { Queue } from "bullmq";
import { redisConnection } from "./redis-connection.js";

export const cleanupQueue = new Queue("cleanup", { connection: redisConnection });
```

```ts title="src/queues/scheduler.ts"
import { cleanupQueue } from "./cleanup-queue.js";

export async function registerRepeatableJobs() {
  await cleanupQueue.add(
    "cleanup-expired-refresh-tokens",
    {},
    {
      repeat: { pattern: "*/30 * * * *" }, // cron: mỗi 30 phút
    },
  );
}
```

<Callout type="info" title="Tên option có thể đã đổi ở phiên bản BullMQ bạn đang dùng">
  API `repeat` mô tả ở đây là cách kinh điển để tạo repeatable job và vẫn là khái niệm cốt lõi cần hiểu. Các phiên bản BullMQ gần đây giới thiệu "Job Schedulers" (`queue.upsertJobScheduler(...)`) như một cách thay thế, tường minh hơn, cho cùng ý tưởng. Luôn đối chiếu tài liệu đúng phiên bản `bullmq` trong `package.json` trước khi copy nguyên văn — tên hàm có thể khác, nhưng bản chất "lịch chạy được lưu ở Redis, không phải trong process" là không đổi.
</Callout>

Khác biệt quan trọng so với `setInterval(fn, 30 * 60 * 1000)` viết tay:

| | `setInterval` tự viết | BullMQ repeatable job |
|---|---|---|
| Nơi lưu lịch | Bộ nhớ (RAM) của đúng process gọi `setInterval` | Redis — bên ngoài mọi process |
| Khi process restart | Mất lịch hoàn toàn, phải tự gọi lại `setInterval` lúc khởi động | Lịch vẫn còn nguyên trong Redis, worker mới kết nối lại là thấy tiếp |
| Chạy nhiều instance worker | Mỗi instance tự chạy `setInterval` riêng → job chạy trùng nhiều lần | BullMQ đảm bảo chỉ một worker lấy được job ở mỗi lần lặp (dựa trên cơ chế lock của Redis) |
| Theo dõi lịch sử chạy | Tự viết log riêng | Có sẵn trong Redis, xem được qua `redis-cli` hoặc UI như Bull Board |

### Processor: idempotent theo thiết kế

```ts title="src/worker.ts"
import { lt, or, isNotNull } from "drizzle-orm";
import { refreshTokens } from "./db/schema.js";

new Worker(
  "cleanup",
  async (job) => {
    if (job.name !== "cleanup-expired-refresh-tokens") return;

    const deleted = await db
      .delete(refreshTokens)
      .where(or(lt(refreshTokens.expiresAt, new Date()), isNotNull(refreshTokens.revokedAt)))
      .returning({ id: refreshTokens.id });

    console.log(`cleanup-expired-refresh-tokens: đã xoá ${deleted.length} dòng`);
  },
  { connection: redisConnection },
);
```

Job này **an toàn khi chạy trùng lặp** mà không cần cơ chế idempotency-key riêng như job `task-status-changed` ở bài trước: `DELETE ... WHERE <điều kiện>` chỉ xoá đúng những dòng còn thoả điều kiện tại đúng thời điểm chạy. Nếu job này lỡ chạy hai lần liên tiếp (ví dụ do trùng lịch, hoặc do retry), lần thứ hai đơn giản là không tìm thấy gì để xoá — không có tác dụng phụ nào chồng lên nhau. Đây là lý do các thao tác dạng "dọn dẹp theo điều kiện" (cleanup, xoá cache hết hạn...) thường là ứng viên tốt cho repeatable job hơn các thao tác dạng "tạo mới vô điều kiện" (như insert notification).

<Callout type="warning" title="Đăng ký repeatable job đúng một lần, không phải mỗi lần worker khởi động lại vô tội vạ">
  Gọi `cleanupQueue.add(...)` với cùng `repeat.pattern` nhiều lần là an toàn (BullMQ nhận diện và không tạo lịch trùng cho cùng tên job + pattern), nhưng vẫn nên gọi `registerRepeatableJobs()` ở một nơi rõ ràng (lúc `worker` khởi động) thay vì rải rác nhiều chỗ trong code — dễ quên đang có bao nhiêu lịch đang chạy.
</Callout>

<Callout type="mistake">
  Viết processor cleanup theo kiểu "lấy hết rồi lặp qua từng dòng để xoá" (`SELECT * ... FOR EACH row DELETE`) thay vì một câu `DELETE ... WHERE` duy nhất. Với bảng `refresh_tokens` tích luỹ hàng chục nghìn dòng hết hạn, cách lặp từng dòng vừa chậm vừa tốn round-trip DB không cần thiết.
</Callout>
