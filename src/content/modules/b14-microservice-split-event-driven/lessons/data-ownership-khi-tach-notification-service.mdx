`notification-service` (B13) hiện đã gọi qua gRPC thay vì hàm nội bộ — nhưng nếu tương lai có ai đó "tiện tay" cho `notification-service` tự kết nối thẳng vào Postgres của `taskflow-api` để đọc `outbox` (thay vì qua relay/gRPC), ranh giới giữa hai service sẽ vỡ. Bài này chốt lại nguyên tắc **data ownership**: mỗi service sở hữu dữ liệu của riêng nó.

<Technical>

### Vì sao `notification-service` không nên đọc thẳng Postgres của `taskflow-api`

`outbox`, `comments`, `tasks`... là schema NỘI BỘ của `taskflow-api` — chi tiết triển khai, không phải hợp đồng công khai. Nếu `notification-service` tự `SELECT` thẳng vào các bảng đó:

- Đổi tên cột, thêm ràng buộc, hay tách bảng ở `taskflow-api` có thể âm thầm làm vỡ `notification-service` — không ai biết cho tới khi lỗi ở production.
- Hai service coi như dùng chung một cơ sở dữ liệu — mất khả năng scale, deploy, hay đổi công nghệ lưu trữ độc lập cho từng service (đúng tinh thần "Database per service" của Chris Richardson).

Thay vào đó, `notification-service` nên có **DB/read model riêng** (ví dụ một bảng `sent_notifications` trong database của chính nó, dùng để dedup và lưu lịch sử gửi) — chỉ nhận dữ liệu qua **contract rõ ràng**: request gRPC `SendNotification` mà relay gửi tới, không hơn không kém.

```proto title="notification-service/proto/notification.proto (đã có từ B13, nhắc lại contract)"
service NotificationService {
  rpc SendNotification(SendNotificationRequest) returns (SendNotificationResponse);
}

message SendNotificationRequest {
  string event_type = 1;
  string aggregate_id = 2;
  string payload = 3; // JSON string — notification-service tự parse theo nhu cầu của nó
}
```

`notification-service` hoàn toàn tự do quyết định lưu gì, ở đâu, bằng công nghệ gì — miễn là implement đúng `.proto` này. Đây chính là ranh giới data ownership: `taskflow-api` không cần biết `notification-service` lưu trữ thế nào, và ngược lại.

### Chaos test: chứng minh "không mất, không trùng" bằng dữ liệu thật

```ts title="src/queues/outbox-relay.chaos.test.ts"
import { execSync } from "node:child_process";
import { describe, expect, it } from "vitest";
import { isNull } from "drizzle-orm";
import { db } from "../db/client.js";
import { outbox } from "../db/schema.js";
import { relayOnce } from "./outbox-relay.js";

describe("outbox relay chịu được notification-service down", () => {
  it("không mất event khi service down rồi phục hồi", async () => {
    execSync("docker compose stop notification-service");

    const createdIds: string[] = [];
    for (let index = 0; index < 5; index += 1) {
      const response = await fetch(`${process.env.API_URL}/api/v1/tasks/${process.env.TEST_TASK_ID}/comments`, {
        method: "POST",
        headers: { "Content-Type": "application/json", Authorization: `Bearer ${process.env.TEST_TOKEN}` },
        body: JSON.stringify({ body: `chaos test #${index}` }),
      });
      expect(response.status).toBe(201); // request chính KHÔNG bị ảnh hưởng dù service phụ trợ đang chết
      const comment = (await response.json()) as { id: string };
      createdIds.push(comment.id);
    }

    const pendingBefore = await db.select().from(outbox).where(isNull(outbox.publishedAt));
    expect(pendingBefore.length).toBeGreaterThanOrEqual(5); // outbox tích tụ, chưa mất dòng nào

    execSync("docker compose start notification-service");
    await new Promise((resolve) => setTimeout(resolve, 3000)); // đợi service sẵn sàng nhận gRPC

    // Poll thủ công vài lượt thay vì đợi relay tự chạy — test chạy nhanh và tất định hơn
    for (let attempt = 0; attempt < 5; attempt += 1) {
      const { attempted } = await relayOnce();
      if (attempted === 0) break;
    }

    const pendingAfter = await db.select().from(outbox).where(isNull(outbox.publishedAt));
    expect(pendingAfter.length).toBe(0); // KHÔNG THIẾU: mọi dòng cuối cùng đều được đánh dấu published_at
  });
});
```

Test này không "giả lập" gì cả — nó thật sự dừng container, thật sự gọi API, thật sự đọc Postgres. Đúng tinh thần "code thật, không giả lập" của course.
