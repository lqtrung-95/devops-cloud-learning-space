Timeline hoạt động y hệt: mỗi user có một "ngăn tủ" (Redis sorted set) chỉ chứa **ID bài viết**, không chứa nội dung. Muốn xem nội dung thật, hệ thống cầm ID ra "kệ sách chung" (post store) lấy về — bước này gọi là **hydrate**.

### API & data model

**API tối thiểu**
- `POST /posts { text, mediaRef? }` → tạo bài, trả `postId`
- `GET /feed?cursor=&limit=20` → trả danh sách bài đã hydrate + `nextCursor`
- `POST /follow/{targetId}`, `DELETE /follow/{targetId}`

**Data model**

| Kho dữ liệu | Vai trò | Vì sao chọn |
|---|---|---|
| Postgres `posts(id, author_id, text, media_ref, created_at)` | Nguồn sự thật của nội dung bài viết | Bền, hỗ trợ transaction, dễ join khi cần audit/xoá (xem lại SD05) |
| Postgres `follows(follower_id, followee_id)` | Đồ thị follow | Quan hệ nhiều-nhiều, cần query "ai follow ai" cho fanout worker |
| Redis `timeline:{userId}` (ZSET, score = `postId`/timestamp) | Danh sách ID bài đã push cho user này | Đọc `ZREVRANGE` O(log N), ghi `ZADD` O(log N) — đúng việc Redis làm tốt |
| Redis `post:{postId}` (hash hoặc string JSON) | Cache nội dung để hydrate nhanh | Tránh đọc Postgres cho mọi lần hydrate; cache-aside như đã học ở SD04 |

### Vì sao lưu ID, không lưu nội dung

Nếu `timeline:{followerId}` lưu cả nội dung bài viết, một celebrity 50 triệu follower đăng 1 bài nghĩa là **50 triệu bản sao** của cùng một nội dung nằm rải rác trong Redis. Tốn storage khủng khiếp, và nếu tác giả sửa hoặc xoá bài, bạn phải phát lại thay đổi đó cho **50 triệu nơi** — chính là bài toán fan-out lần thứ hai, lần này cho update.

Lưu `postId` giữ nguyên tắc: **một nội dung, một nơi lưu (post store); timeline chỉ là danh sách con trỏ**. Sửa/xoá bài chỉ cần cập nhật đúng một chỗ.

### Đọc feed: hydrate & merge celebrity

1. `ZREVRANGE timeline:{userId} 0 19` → 20 `postId` gần nhất (đã có sẵn nhờ push của lesson trước).
2. Với mỗi celebrity mà user đang follow, lấy trực tiếp K bài mới nhất của họ (`ZREVRANGE posts:{celebrityId} 0 K` hoặc query Postgres) — đây là phần "pull" trong hybrid, chi phí không phụ thuộc follower count của celebrity.
3. Merge hai danh sách theo thời gian, cắt còn 20 bài đầu.
4. **Hydrate**: batch lấy nội dung cho toàn bộ `postId` bằng pipeline/`MGET` tới Redis post cache; cache miss thì query Postgres `WHERE id IN (...)` rồi nạp lại cache.
5. Trả JSON kèm `nextCursor` cho lần load tiếp theo.

```ts title="src/services/get-feed.ts"
async function getFeed(userId: string, limit = 20) {
  const ownIds = await redis.zrevrange(`timeline:${userId}`, 0, limit - 1);
  const celebIds = await getFollowedCelebrityIds(userId); // thường rất ít (vài chục)
  const pulled = await Promise.all(celebIds.map((id) => redis.zrevrange(`posts:${id}`, 0, 3)));
  const merged = mergeByTimestamp(ownIds, pulled.flat()).slice(0, limit);

  const cached = await redis.mget(merged.map((id) => `post:${id}`));
  const missingIds = merged.filter((id, i) => cached[i] === null);
  const fromDb = missingIds.length ? await db.query("SELECT * FROM posts WHERE id = ANY($1)", [missingIds]) : [];
  await Promise.all(fromDb.map((post) => redis.set(`post:${post.id}`, JSON.stringify(post), "EX", 300)));

  return hydrate(merged, cached, fromDb);
}
```

### Trimming: đừng để timeline phình vô hạn

Mỗi lần `ZADD`, kèm theo `ZREMRANGEBYRANK timeline:{userId} 0 -1001` để chỉ giữ 1.000 bài gần nhất — user hiếm khi cuộn quá sâu, và timeline không thể lớn mãi theo thời gian tồn tại của tài khoản.

### Ranking (khái niệm)

Mặc định feed sắp theo thời gian (reverse chronological) — đơn giản, dễ giải thích, đủ cho phần lớn thiết kế phỏng vấn cấp mid–senior. Feed dựa trên **engagement/ML ranking** thay điểm sắp xếp bằng một model dự đoán mức độ quan tâm — đó là một hệ thống ML riêng (feature store, model serving) nằm ngoài phạm vi module này; điều cần biết là **retrieval (lấy ứng viên) và ranking (sắp xếp) là hai tầng tách rời**, module này chỉ lo tầng đầu.

| Lựa chọn | Ưu | Nhược | Dùng khi |
|---|---|---|---|
| Lưu ID + hydrate | Storage nhỏ, sửa/xoá bài chỉ 1 chỗ | Thêm 1 bước round-trip hydrate | Mặc định cho mọi hệ thống feed thật |
| Lưu full content trong timeline | Đọc feed không cần hydrate, nhanh hơn 1 bước | Storage nhân theo follower; update/xoá phải fan-out lại | Chỉ hợp khi bài viết bất biến và follower rất ít (hiếm khi đúng) |
| Chronological mặc định | Dễ cài, dễ giải thích, không cần model | Không tối ưu engagement | Giai đoạn đầu, hoặc phạm vi phỏng vấn không yêu cầu ranking |

<Callout type="mistake" title="Hydrate tuần tự từng bài một">
  Lấy 20 `postId` rồi gọi 20 lần `GET post:{id}` tuần tự nhân độ trễ mạng lên 20 lần round-trip. Luôn dùng batch (`MGET`, pipeline, hoặc `WHERE id IN (...)`).
</Callout>

<Callout type="warning" title="Celebrity vẫn cần một nơi lưu 'bài mới nhất' để pull">
  Nếu celebrity bị loại hoàn toàn khỏi cơ chế push, bạn vẫn cần một cấu trúc để tra "K bài mới nhất của celebrity X" nhanh — thường vẫn là một ZSET (`posts:{celebrityId}`), chỉ khác là **không nhân theo follower**, chỉ có đúng 1 bản.
</Callout>

<Callout type="info" title="Góc phỏng vấn">
  Khi bị hỏi "feed lưu gì", câu trả lời mạnh là: **ID + hydrate**, giải thích rõ đánh đổi (thêm 1 round-trip nhưng tiết kiệm storage và tránh fan-out lại khi sửa/xoá bài). Nếu bị hỏi sâu về ranking, thừa nhận đó là một hệ thống ML riêng và tập trung vào phần retrieval bạn vừa thiết kế — đừng cố bịa một công thức ranking phức tạp nếu không được hỏi.
</Callout>
