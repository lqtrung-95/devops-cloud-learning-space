Bài trước cho thấy `Task.comments` và `Comment.author` là resolver riêng, chạy độc lập cho TỪNG phần tử cha. Đây chính là cơ chế tạo ra vấn đề N+1 — không phải lỗi code sai, mà là hệ quả tự nhiên của mô hình "mỗi field một resolver" nếu không ai chủ động gom lại.

<Technical>

### N+1 ở GraphQL khác N+1 ở REST như thế nào

B04 đã dạy N+1 cho REST (`n-cong-1-query-relational-query-api`) và cách Drizzle relational query API tự gộp thành 2 câu SQL cho MỘT hình dạng dữ liệu cụ thể (task kèm comment). Nhưng đó là giải pháp gắn với đúng 1 câu query REST viết sẵn.

GraphQL cho client tự chọn shape bất kỳ (`project { tasks { comments { author } } }`, hoặc `project { tasks { comments } }` không cần author, hoặc thêm `assignee` — vô số tổ hợp). Không thể viết sẵn một câu SQL tối ưu cho MỌI tổ hợp có thể — mỗi field vẫn phải là resolver độc lập. N+1 vì vậy là vấn đề **cấu trúc**, cần giải pháp áp dụng theo TỪNG field (DataLoader), không phải theo từng query cụ thể.

### Đo N+1 bằng log SQL thật, không đoán

```ts title="src/db/client.ts (bật lại từ B04)"
export const db = drizzle(client, { schema, logger: true });
```

Với `logger: true`, mỗi câu SQL Drizzle chạy sẽ in ra console. Chạy query `project { tasks { comments { author { name } } } }` cho 1 project có 3 task, mỗi task 2 comment (6 comment), MỖI comment có tác giả khác nhau — và đếm dòng log:

```text
Query: select * from "projects" where "id" = $1                         -- 1: Query.project
Query: select * from "tasks" where "project_id" = $1                    -- 1: Project.tasks
Query: select * from "comments" where "task_id" = $1                    -- 3: Task.comments (task 1)
Query: select * from "comments" where "task_id" = $1                    --    Task.comments (task 2)
Query: select * from "comments" where "task_id" = $1                    --    Task.comments (task 3)
Query: select * from "users" where "id" = $1                            -- 6: Comment.author (comment 1)
Query: select * from "users" where "id" = $1                            --    ... (comment 2..6)
```

Tổng: 1 + 1 + 3 + 6 = **11 câu SQL** cho một query GraphQL duy nhất — đây là con số thật cần fix, không phải cảm nhận "chắc là chậm".

### DataLoader: gom key trong cùng tick, phát 1 query `IN (...)`

```ts title="src/graphql/loaders/user-loader.ts"
import DataLoader from "dataloader";
import { inArray } from "drizzle-orm";
import { db } from "../../db/client.js";
import { users, type User } from "../../db/schema.js";

export function createUserLoader() {
  return new DataLoader<string, User | null>(async (ids) => {
    const rows = await db.select().from(users).where(inArray(users.id, [...ids]));
    // BẮT BUỘC trả về đúng thứ tự và đúng số lượng như `ids` — DataLoader dựa vào vị trí để khớp kết quả
    return ids.map((id) => rows.find((row) => row.id === id) ?? null);
  });
}
```

`new DataLoader(batchFn)` không tự chạy `batchFn` ngay khi `.load(id)` được gọi. Nó gom TẤT CẢ các lệnh `.load()` xảy ra trong CÙNG một tick của event loop (microtask hiện tại), rồi mới gọi `batchFn` đúng MỘT LẦN với mảng tất cả các `id` đã gom được.

```ts title="src/plugins/graphql.ts — tạo loader MỚI mỗi request"
context: async (request) => {
  await request.jwtVerify();
  return {
    userId: request.user.sub,
    userLoader: createUserLoader(), // instance MỚI cho MỖI request, không dùng chung toàn app
  };
},
```

```ts title="src/graphql/resolvers.ts"
Comment: {
  author: async (parent, _args, context) => context.userLoader.load(parent.authorId),
},
```

Sau khi 6 resolver `Comment.author` cùng gọi `.load(authorId)` trong cùng tick, DataLoader phát đúng 1 câu `SELECT * FROM users WHERE id IN (id1, ..., id6)`. Đếm lại log SQL: 1 (project) + 1 (tasks) + 3 (comments, CHƯA fix ở bài này) + 1 (author, đã gộp) = **6 câu SQL** — giảm từ 11 xuống 6 chỉ bằng cách fix đúng 1 field.

### Vì sao phải tạo loader MỚI mỗi request

DataLoader cache kết quả trong bộ nhớ theo mặc định, trong suốt vòng đời của CHÍNH instance đó. Nếu tạo `createUserLoader()` một lần lúc khởi động app rồi dùng chung cho mọi request, kết quả `.load(userId)` của request A có thể được trả thẳng cho request B mà không hề query lại — không chỉ sai dữ liệu (nếu user vừa đổi tên) mà còn có thể rò rỉ dữ liệu giữa các request nếu logic sau này có phân biệt quyền theo user gọi. Vì vậy: **1 request = 1 loader instance mới**, không cache xuyên request.

<Callout type="mistake" title="DataLoader không cache xuyên request">
  Một lỗi thật hay gặp: khởi tạo `const userLoader = createUserLoader();` ở ngoài cùng file `app.ts`, dùng lại cho mọi request thay vì tạo mới trong `context`. Ban đầu vẫn chạy bình thường (thậm chí NHANH hơn vì cache), nhưng đây là bug tiềm ẩn: dữ liệu cache từ request trước lọt sang request sau, và nếu sau này có field nhạy cảm phụ thuộc quyền của user gọi, request B có thể vô tình nhận cache của request A. Luôn tạo loader mới trong hàm `context`.
</Callout>
