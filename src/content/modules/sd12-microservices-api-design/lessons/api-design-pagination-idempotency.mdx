### Resource naming & versioning

- Dùng **danh từ số nhiều** cho resource: `/orders`, `/orders/{id}/items`, không phải `/getOrder` hay `/order-service/fetch`.
- Lồng resource khi có quan hệ sở hữu rõ ràng: `/orders/{id}/items`, nhưng đừng lồng quá 2 cấp — `/users/{id}/orders/{id}/items/{id}/notes` khó dùng.
- **Versioning:** đặt version ở URI (`/v1/orders`) đơn giản, dễ thấy khi debug; đặt ở header (`Accept: application/vnd.api+json;version=1`) "sạch" hơn về mặt REST nhưng khó grep log hơn. Chọn 1 cách và nhất quán toàn hệ thống — đổi version là **breaking change**, không đổi ngầm field cũ.

### Offset vs cursor (keyset) pagination

`OFFSET n LIMIT m` yêu cầu Postgres **đọc và bỏ qua n dòng** trước khi trả về m dòng — kể cả khi có index trên cột sắp xếp, `OFFSET` không "nhảy thẳng" tới vị trí. Trang càng sâu, chi phí quét càng lớn.

`WHERE id > $lastId ORDER BY id LIMIT m` (cursor/keyset) dùng index seek để nhảy thẳng tới vị trí sau `$lastId`, luôn quét cỡ đúng `m` dòng bất kể đang ở "trang" nào.

| Tiêu chí | Offset pagination | Cursor (keyset) pagination |
|---|---|---|
| Chi phí ở trang sâu | Tăng tuyến tính theo độ sâu — `OFFSET 5.000.000` vẫn phải quét ~5 triệu dòng | Gần như hằng số nhờ index seek trên cột cursor |
| Nhảy thẳng tới "trang N" | Có (`OFFSET (N-1)*limit`) | Không — chỉ đi tiếp/lùi tuần tự từ cursor hiện có |
| Dữ liệu bị chèn/xoá giữa các lần đọc | Có thể bị trùng/bỏ sót dòng (dòng dịch chuyển vị trí offset) | Ổn định hơn — cursor bám theo giá trị cột, không bám theo vị trí |
| Dùng khi | UI cần hiện số trang, dữ liệu nhỏ/vừa | Infinite scroll, feed, dataset lớn, API công khai cho bên thứ ba |

**Khi nào đổi ý:** nếu UI thực sự cần "nhảy tới trang 500" và dữ liệu đủ lớn để offset chậm, cân nhắc đánh index vật lý theo trang định kỳ (partition/pre-compute) thay vì ép dùng offset trên bảng sống.

### Idempotent POST bằng idempotency key

HTTP định nghĩa `GET`/`PUT`/`DELETE` là idempotent (gọi lại nhiều lần cho kết quả như gọi 1 lần), nhưng `POST` thì **không** — gọi lại `POST /orders` mặc định tạo thêm 1 đơn mới. Khi client cần retry an toàn (timeout, mất kết nối giữa lúc server đã xử lý xong), giải pháp chuẩn: client tự sinh 1 `Idempotency-Key` (thường là UUID) gửi kèm header, server lưu `(key, request_hash, response)` vào bảng riêng; nếu thấy key đã tồn tại, trả lại đúng response cũ thay vì xử lý lại. Nếu cùng key nhưng payload khác, trả lỗi `409 Conflict` — tránh trường hợp key bị dùng sai cho 2 request khác nhau.

### Error format nhất quán

Trả lỗi theo 1 format cố định trên toàn hệ thống, không phải chuỗi tự do:

```json
{
  "error": {
    "code": "INVENTORY_INSUFFICIENT",
    "message": "Không đủ hàng cho sku-42",
    "requestId": "req-8f2a1c"
  }
}
```

`code` để client code xử lý theo logic (switch/case), `message` để hiển thị/debug, `requestId` để nối với distributed tracing khi cần tra log. RFC 7807 (`application/problem+json`) là một chuẩn tham khảo tốt nếu muốn thứ gì đó được công nhận rộng rãi.

<Callout type="mistake" title="Tưởng POST đã idempotent sẵn vì có unique constraint trên sku+timestamp">
  Unique constraint đúng cho 1 lần chèn, nhưng nếu request retry có timestamp khác (do client tạo lại object trước khi gửi lại) thì constraint không bắt được — vẫn tạo đơn trùng. Idempotency key phải do CLIENT sinh một lần duy nhất cho cả vòng đời của thao tác đó (kể cả khi retry), không phải sinh mới mỗi lần gọi.
</Callout>

<Callout type="warning" title="OFFSET giả vờ nhanh khi test với dữ liệu nhỏ">
  `EXPLAIN ANALYZE` với 1.000 dòng thì offset trang sâu vẫn nhanh — bẫy phổ biến là test pagination với dataset nhỏ rồi kết luận "không sao". Chi phí `OFFSET n` chỉ lộ rõ khi n đủ lớn (hàng trăm nghìn tới hàng triệu), đúng như lab seed 5 triệu dòng ở trên.
</Callout>

<Callout type="info" title="Góc phỏng vấn">
  "Thiết kế API list resource cho dataset lớn, hỗ trợ infinite scroll" gần như luôn kỳ vọng bạn đề xuất cursor pagination thay vì offset, và giải thích được TẠI SAO offset chậm (`OFFSET` vẫn phải quét/bỏ qua n dòng) chứ không chỉ nói "cursor nhanh hơn". Thêm điểm nếu bạn tự nêu đánh đổi: cursor không hỗ trợ nhảy thẳng tới số trang bất kỳ.
</Callout>
