### Validate TRƯỚC khi tốn công ký URL

Nguyên tắc thứ tự quan trọng: kiểm tra `sizeBytes`/`mimeType` phải xảy ra **trước** lời gọi `getSignedUrl`. Không phải vì ký URL tốn kém (nó rẻ), mà vì để giữ đúng ngữ nghĩa — nếu khai báo sai ngay từ đầu, không nên có bất kỳ URL hợp lệ nào được tạo ra cho request đó.

```ts title="src/routes/attachments.ts"
const MAX_ATTACHMENT_SIZE_BYTES = 15 * 1024 * 1024; // 15 MB
const ALLOWED_ATTACHMENT_MIME_TYPES = ["image/png", "image/jpeg", "application/pdf"] as const;

function assertAttachmentClaimAllowed(sizeBytes: number, mimeType: string) {
  if (sizeBytes > MAX_ATTACHMENT_SIZE_BYTES) {
    throw new ApiError(400, "VALIDATION_ERROR", `File tối đa ${MAX_ATTACHMENT_SIZE_BYTES / 1024 / 1024}MB, khai báo ${(sizeBytes / 1024 / 1024).toFixed(1)}MB`);
  }
  if (!ALLOWED_ATTACHMENT_MIME_TYPES.includes(mimeType as (typeof ALLOWED_ATTACHMENT_MIME_TYPES)[number])) {
    throw new ApiError(400, "VALIDATION_ERROR", `mimeType "${mimeType}" không được hỗ trợ`);
  }
}
```

Handler gọi hàm này **trước** dòng `getSignedUrl(...)` — nếu ném lỗi, error handler chung (chốt ở B03) bắt và trả `400` theo đúng format `{ error: { code, message } }`, không có S3 client nào được gọi tới.

### Vì sao bước này "cần thiết nhưng chưa đủ"

Tất cả những gì server biết ở bước presign là **client tự khai** — không phải sự thật đã được xác minh. Một presigned PUT URL sau khi được ký chỉ ràng buộc:

- **Method**: phải là `PUT` (không GET/DELETE được)
- **Key**: phải đúng object key đã ký
- **Thời hạn**: hết hiệu lực sau `expiresIn` giây

Nó **không** tự động ràng buộc: dung lượng byte thật client gửi trong request PUT, hay nội dung thật của file có khớp với `Content-Type` đã khai hay không. (Muốn ràng buộc dung lượng ở tầng chữ ký, cần dùng **presigned POST với policy conditions** — ví dụ `content-length-range` — một cơ chế khác với presigned PUT mà `taskflow-api` đang dùng ở B08.)

Nghĩa là: một client cố tình khai `sizeBytes: 500000` (500KB, qua được validate) nhưng lúc PUT thật lại gửi file 50MB — request PUT đó **vẫn thành công** vì presigned PUT URL không kiểm tra lại dung lượng. Server chỉ phát hiện ra sai lệch này ở bước sau: `HeadObjectCommand` khi confirm (bài tiếp theo).

<Callout type="warning" title="Không bao giờ tin Content-Length hay đuôi file để quyết định an toàn">
  `Content-Length` và đuôi file (`.png`, `.pdf`) đều là dữ liệu **client tự đặt**, không phải bằng chứng khách quan. Một file thực thi đổi tên thành `ảnh.png` và khai `Content-Type: image/png` vượt qua validate y hệt một ảnh PNG thật. Validate ở bước presign chặn được người dùng vô ý nhầm định dạng — không chặn được người cố tình giả mạo.
</Callout>

### Trade-off: chặn chặt ở presign vs. để storage/scan xử lý

| Lựa chọn | Ưu | Nhược | Dùng khi |
|---|---|---|---|
| Chỉ validate ở presign (metadata khai báo) | Đơn giản, phản hồi nhanh (400 ngay, không cần upload) | Không chặn được client khai gian lúc PUT thật | Bước lọc đầu tiên, rẻ — luôn nên có |
| Presigned POST + policy `content-length-range` | S3/MinIO tự chặn ở tầng storage nếu vượt size — không cần chờ tới HEAD check | Phức tạp hơn PUT thường, một số client (đặc biệt upload từ script đơn giản) khó tích hợp | Khi cần ràng buộc size chặt ngay ở storage, không chỉ ở app |
| HEAD check + scan sau upload (bài tiếp theo, nối B09) | Bắt được cả trường hợp client nói dối lúc PUT | Chạy sau khi file đã tốn dung lượng lưu trữ, cần dọn dẹp nếu phát hiện sai | Lưới an toàn cuối cùng — luôn cần, dù đã có 2 lớp trên |

</Technical>
