<Eli5 title="Kubernetes giống như ban quản lý một cảng container" emoji="⚓">

Ở M04 bạn đã học đóng gói app thành **container** — những thùng hàng chuẩn. Chạy 3 thùng trên 1 máy thì dễ. Nhưng khi có **300 thùng trên 20 máy**, ai quyết định thùng nào đặt ở đâu? Thùng bị hỏng lúc 3 giờ sáng thì ai thay? Khách muốn tìm "quầy api" thì hỏi ai?

**Kubernetes** là **ban quản lý cảng**. Bạn không chỉ tay "đặt thùng này lên cầu tàu số 4". Bạn nộp một **tờ kế hoạch**: "tôi muốn luôn có 3 thùng loại `web`". Ban quản lý ghi vào **sổ cái**, cử người **xếp chỗ**, và có **đội đi tuần** liên tục so kế hoạch với thực tế — thiếu thùng thì bổ sung.

Mỗi **cầu tàu (node)** có một **đốc công (kubelet)** nhận việc từ ban quản lý và bảo công nhân (container runtime) mở thùng.

Chỗ phép so sánh "gãy": thùng hàng thật bị hỏng thì sửa; còn pod hỏng thì Kubernetes **vứt đi và tạo cái mới** — pod là đồ dùng một lần.

</Eli5>

## Vì sao DevOps cần Kubernetes?

Docker Compose chạy tốt trên **một** máy. Production cần: nhiều máy, tự thay thế khi hỏng, rolling update không downtime, tự scale, service discovery, quản lý cấu hình/secret thống nhất. Kubernetes gom tất cả vào **một API khai báo** — và đó là nền tảng của EKS (M13), GitOps (M14) và kỳ thi **CKA**.

<Technical>

### Control plane — bộ não

| Thành phần | Việc chính | Ghi nhớ |
|---|---|---|
| `kube-apiserver` | REST API: authn → authz (RBAC) → admission → ghi etcd | Cửa ngõ **duy nhất** vào etcd |
| `etcd` | Key-value store phân tán (Raft) lưu mọi object | Backup định kỳ! Cần số node lẻ (3, 5) |
| `kube-scheduler` | Gán pod chưa có `nodeName` cho node phù hợp | Lọc (filter) rồi chấm điểm (score) |
| `kube-controller-manager` | Chạy các controller: Deployment, ReplicaSet, Node, Job… | Mỗi controller = một vòng lặp reconcile |
| `cloud-controller-manager` | Nói chuyện với cloud: tạo load balancer, gắn node | Có trên EKS/GKE, không có trên kind |

### Worker node — tay chân

- **kubelet**: watch pod được gán cho node mình, gọi runtime qua **CRI**, chạy probes, báo status.
- **container runtime**: `containerd` hoặc `CRI-O`. Docker Engine không còn được kubelet dùng trực tiếp từ v1.24 (dockershim bị gỡ) — nhưng image build bằng Docker vẫn chạy bình thường vì cùng chuẩn OCI.
- **kube-proxy**: biến IP ảo của Service thành luật iptables/nftables/IPVS. Một số CNI (Cilium) thay thế luôn kube-proxy.
- **CNI plugin**: cấp IP cho pod, nối mạng giữa các node (kindnet, Calico, Cilium, Amazon VPC CNI).

### Chuyện gì xảy ra khi `kubectl apply -f deploy.yaml`?

1. `kubectl` gửi object tới API server → xác thực, kiểm tra quyền, chạy admission → lưu vào etcd.
2. **Deployment controller** thấy Deployment mới → tạo **ReplicaSet**.
3. **ReplicaSet controller** thấy thiếu pod → tạo 3 object Pod (chưa có node).
4. **Scheduler** thấy pod chưa có node → chọn node → ghi `spec.nodeName`.
5. **kubelet** trên node đó thấy pod của mình → gọi containerd pull image và chạy container.
6. kubelet báo status `Running` → API server → etcd. Bạn thấy nó trong `kubectl get pods`.

Để ý: **không ai ra lệnh trực tiếp cho ai**. Mọi thành phần chỉ *watch* API server và tự làm phần việc của mình. Đó là lý do Kubernetes chịu lỗi tốt.

### Khai báo (declarative) — mọi object đều có 4 phần

```yaml title="hello-pod.yaml"
apiVersion: v1          # nhóm API + phiên bản
kind: Pod               # loại object
metadata:
  name: hello
  labels:
    app: hello
spec:                   # trạng thái MONG MUỐN (bạn viết)
  containers:
    - name: hello
      image: nginx:1.27
      ports:
        - containerPort: 80
# status:               # trạng thái THỰC TẾ (Kubernetes điền)
```

### Công cụ học tập

| Công cụ | Dùng khi |
|---|---|
| `kind` | Cluster nhiều node chạy trong Docker — nhanh, hợp CI và lab |
| `minikube` | Cluster local có nhiều addon sẵn |
| `kubectl` | CLI chính thức, dùng trong kỳ thi CKA |
| `k9s` | Giao diện terminal để duyệt cluster nhanh |
| `kubectx` / `kubens` | Đổi cluster / namespace mặc định |

</Technical>

<Callout type="mistake">

**Chạy "pod trần" (không có Deployment) cho app thật.** Pod chỉ là một thùng hàng — node chết hoặc bạn xoá nó thì mất luôn, không ai tạo lại. Luôn để một controller (Deployment, StatefulSet, Job…) quản lý pod.

</Callout>
