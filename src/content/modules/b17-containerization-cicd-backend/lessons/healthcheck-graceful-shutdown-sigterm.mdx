### Liveness vs readiness — vì sao `/api/v1/health` không đủ

`/api/v1/health` (B01) trả `{ "status": "ok" }` vô điều kiện — nó chỉ chứng minh **process Node.js còn chạy** (liveness). Nó không chứng minh **service còn phục vụ được** (readiness): nếu Postgres chết, mọi request CRUD đều sẽ lỗi 500, nhưng `/api/v1/health` vẫn cười tươi trả 200.

```ts title="src/routes/healthz.ts"
import type { FastifyInstance } from "fastify";
import { sql } from "drizzle-orm";
import { db } from "../db/client.js";
import { redis } from "../lib/redis-client.js";

export async function healthzRoute(fastify: FastifyInstance) {
  fastify.get("/healthz", async (_request, reply) => {
    const [postgres, redisCheck] = await Promise.allSettled([db.execute(sql`select 1`), redis.ping()]);

    const checks = {
      postgres: postgres.status === "fulfilled" ? "ok" : "down",
      redis: redisCheck.status === "fulfilled" ? "ok" : "down",
    };
    const healthy = checks.postgres === "ok" && checks.redis === "ok";

    return reply.status(healthy ? 200 : 503).send({ status: healthy ? "ok" : "degraded", checks });
  });
}
```

`/healthz` đặt NGOÀI prefix `/api/v1` (mục 3 curriculum) và không qua middleware auth — đây là endpoint hạ tầng dùng cho Docker `HEALTHCHECK` và (sau này) load balancer, không phải resource nghiệp vụ cho client gọi trực tiếp.

### SIGTERM: đóng đúng thứ tự, không chỉ `process.exit()`

```ts title="src/app.ts (phần dưới file, sau hàm buildApp() đã có từ B02)"
import { client } from "./db/client.js";
import { redis } from "./lib/redis-client.js";

const app = buildApp();

await app.listen({ port: 3000, host: "0.0.0.0" });

let shuttingDown = false;

async function shutdown(signal: string) {
  if (shuttingDown) return; // tránh chạy 2 lần nếu signal tới liên tiếp
  shuttingDown = true;
  app.log.info(`Nhận ${signal}, bắt đầu graceful shutdown`);

  try {
    // app.close() ngừng nhận connection MỚI và đợi request đang xử lý hoàn tất
    await app.close();
    // Chỉ đóng pool SAU KHI chắc chắn không còn request nào đang dùng chúng
    await client.end();
    await redis.quit();
    app.log.info("Đóng sạch, thoát process");
    process.exit(0);
  } catch (error) {
    app.log.error(error, "Lỗi khi shutdown, thoát cưỡng bức");
    process.exit(1);
  }
}

process.on("SIGTERM", () => void shutdown("SIGTERM"));
process.on("SIGINT", () => void shutdown("SIGINT"));
```

```ts title="src/db/client.ts (sửa 1 dòng so với B04)"
import postgres from "postgres";
import { drizzle } from "drizzle-orm/postgres-js";
import * as schema from "./schema.js";

const connectionString = process.env.DATABASE_URL ?? "postgres://taskflow:taskflow@postgres:5432/taskflow";

// Trước B17: "const client = ...". Giờ export để B17 gọi client.end() lúc shutdown.

```

### `docker stop` và giới hạn 10 giây

`docker stop api` gửi `SIGTERM`, đợi **grace period** (mặc định 10 giây, chỉnh bằng `docker stop -t <giây>`), rồi gửi `SIGKILL` nếu process chưa thoát. `SIGKILL` không thể bắt được — không có cơ hội chạy thêm bất kỳ dòng dọn dẹp nào. Toàn bộ chuỗi `app.close()` → `client.end()` → `redis.quit()` phải hoàn tất trong khoảng đó; nếu một request đơn lẻ mất hơn 10 giây, nó vẫn bị cắt ngang dù đã có graceful shutdown.

| Lựa chọn | Ưu | Nhược | Dùng khi |
|---|---|---|---|
| `process.exit(0)` ngay khi nhận `SIGTERM` | Đơn giản, thoát tức thì | Cắt ngang mọi request đang xử lý, để lại connection Postgres/Redis mồ côi | Không nên dùng cho service nhận traffic thật |
| `app.close()` rồi mới đóng pool (cách bài này chọn) | Không mất request đang xử lý; đóng pool đúng lúc an toàn | Cần đảm bảo tổng thời gian dưới grace period của `docker stop` | `taskflow-api` — mọi service Fastify production |
| Tăng grace period (`docker stop -t 30`) | Cho phép request dài hơn hoàn tất | Container mất nhiều thời gian hơn để dừng hẳn, ảnh hưởng tốc độ rolling deploy | Có endpoint biết trước sẽ chạy lâu (export dữ liệu, batch job) |

<Callout type="mistake">
  Gọi `client.end()`/`redis.quit()` TRƯỚC `app.close()`. Nếu pool đóng trước, bất kỳ request nào đang xử lý dở mà cần query DB sẽ nhận lỗi "connection closed" giữa chừng — đúng thứ graceful shutdown cố tránh, chỉ là chuyển từ "connection bị cắt" sang "query bị lỗi". Thứ tự luôn là: ngừng nhận request mới → đợi request cũ xong → mới đóng pool.
</Callout>

<Callout type="warning" title="/healthz không thay thế alerting">
  `/healthz` trả `503` đúng lúc dependency chết, nhưng đó là điều kiện CẦN để orchestrator (Docker, load balancer) ngừng route traffic tới instance đó — không phải điều kiện ĐỦ để đội vận hành biết có sự cố. Observability thật (B16: log có `requestId`, metrics) mới là thứ giúp con người phát hiện và phản ứng kịp thời; `/healthz` chỉ nói cho MÁY biết, không tự thông báo cho NGƯỜI.
</Callout>
