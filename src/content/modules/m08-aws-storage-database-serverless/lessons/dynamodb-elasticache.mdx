<Eli5 title="DynamoDB giống dãy tủ gửi đồ đánh số, ElastiCache giống tủ lạnh cạnh bếp" emoji="🧊">

**DynamoDB** giống **dãy tủ gửi đồ ở siêu thị**: bạn đưa **mã tủ** (partition key) là lấy được đồ trong tích tắc, dù có hàng triệu tủ. Nhưng nếu bạn hỏi "tìm giúp tôi mọi túi màu đỏ" thì nhân viên phải mở từng tủ (Scan) — chậm và tốn.

**ElastiCache (Redis)** giống **tủ lạnh ngay cạnh bếp nhà hàng**. Nguyên liệu gốc nằm ở kho (database). Món hay dùng thì để sẵn trong tủ lạnh: lấy nhanh hơn nhiều, nhưng tủ nhỏ, đồ để lâu sẽ **hết hạn** (TTL), và tủ lạnh không thay được kho.

Cách bếp làm việc: **mở tủ lạnh trước** → có thì dùng luôn → không có thì ra kho lấy, **mang về một phần cất tủ lạnh**. Đó là pattern **cache-aside**.

</Eli5>

Không phải dữ liệu nào cũng hợp với SQL. Session, giỏ hàng, IoT event, leaderboard thường hợp với key-value. Và thêm cache đúng cách thường là cách rẻ nhất để giảm tải cho RDS trước khi nghĩ tới instance to hơn.

<Technical>

### DynamoDB: thiết kế theo cách truy cập

- **Primary key** = `partition key` (bắt buộc) + `sort key` (tuỳ chọn). Partition key được băm để quyết định item nằm ở partition nào.
- Chọn partition key **nhiều giá trị, phân bố đều** (vd `customerId`). Key như `status` hay `date` dễ tạo **hot partition** → throttle.
- `Query` lấy theo partition key (+ điều kiện sort key) — hiệu quả. `Scan` đọc cả bảng — tránh trong đường nóng.
- Cần truy vấn theo thuộc tính khác → **GSI** (Global Secondary Index); LSI dùng chung partition key, phải tạo cùng lúc với bảng.
- Item tối đa 400 KB. Đọc mặc định *eventually consistent*; có thể yêu cầu *strongly consistent* (không áp dụng cho GSI).

| Capacity mode | Khi nào |
|---|---|
| On-demand (`PAY_PER_REQUEST`) | Tải khó đoán, app mới, dev/test — trả theo request |
| Provisioned (+ auto scaling) | Tải ổn định, dự đoán được — thường rẻ hơn khi dùng đều |

Tính năng hay gặp: **TTL** (tự xoá item hết hạn), **Streams** (bắt thay đổi → Lambda), **Global tables** (multi-region active-active), **DAX** (cache chuyên cho DynamoDB), PITR backup.

### ElastiCache: cache trong VPC

- Engine: **Valkey / Redis OSS** (cấu trúc dữ liệu phong phú, replication, persistence tuỳ chọn) hoặc **Memcached** (đơn giản, đa luồng, không replication). Danh sách engine thay đổi theo thời gian — kiểm tra tài liệu mới nhất.
- Chỉ truy cập trong VPC; SG mở port 6379 từ SG của app. Bật **encryption in-transit** và AUTH/RBAC.
- Replication group có replica ở AZ khác + **automatic failover / Multi-AZ** để cache không thành điểm hỏng đơn lẻ.

### Các chiến lược cache

| Chiến lược | Cách làm | Đánh đổi |
|---|---|---|
| Cache-aside (lazy loading) | Đọc cache → miss thì đọc DB và SET | Chỉ cache thứ được đọc; lần đầu chậm; có thể cũ |
| Write-through | Mỗi lần ghi DB thì ghi luôn cache | Cache luôn mới; cache cả dữ liệu không ai đọc |
| TTL | Mọi key có hạn | Giới hạn độ cũ tối đa, tránh cache phình mãi |

```python title="product_repository.py — cache-aside"
def get_product(product_id: str) -> dict:
    key = f"product:{product_id}"
    cached = redis.get(key)
    if cached:
        return json.loads(cached)          # cache hit
    product = db.fetch_product(product_id)  # cache miss → nguồn sự thật
    redis.set(key, json.dumps(product), ex=300)
    return product

def update_price(product_id: str, price: int) -> None:
    db.update_price(product_id, price)
    redis.delete(f"product:{product_id}")  # invalidate sau khi ghi DB
```

<Callout type="mistake">

**Thiết kế DynamoDB như bảng SQL rồi dùng `Scan` + filter.** Filter chạy **sau khi** đã đọc (và tính tiền) toàn bộ dữ liệu quét. Với DynamoDB, liệt kê các câu truy vấn trước, rồi thiết kế key/GSI để mỗi câu là một `Query`.

</Callout>

<Callout type="warning">

Cache **không phải** nguồn sự thật. Redis có thể bị evict key khi đầy bộ nhớ, hoặc mất dữ liệu khi node lỗi. App phải chạy đúng (chỉ chậm hơn) khi cache trống.

</Callout>

<Callout type="cost">

Node ElastiCache tính tiền theo giờ dù không có request. Với dev, 1 node nhỏ là đủ; DynamoDB on-demand hợp với lab vì gần như không tốn khi không dùng.

</Callout>
