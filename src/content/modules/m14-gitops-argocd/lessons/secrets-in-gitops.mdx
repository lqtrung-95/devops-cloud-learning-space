<Eli5 title="Secret trong GitOps giống gửi bưu kiện: hoặc gửi vỏ hộp trống kèm địa chỉ kho, hoặc khoá kín hộp trước khi gửi" emoji="📦">

GitOps đòi hỏi commit **mọi thứ** vào Git — nhưng password DB thì **tuyệt đối không được nằm dạng đọc được** trong Git, kể cả private repo (lịch sử Git tồn tại mãi, ai có quyền đọc repo cũng đọc được commit cũ).

Có hai cách giải bài toán này:

- **External Secrets Operator**: bạn chỉ gửi **một tờ giấy ghi địa chỉ kho** ("secret thật nằm ở AWS Secrets Manager, tên `shop/postgres-password`"). Nhân viên trong cluster tự đi lấy hàng thật từ kho đó.
- **Sealed Secrets**: bạn **khoá kín hộp** bằng ổ khoá đặc biệt (mã hoá bằng public key của cluster đích) rồi mới gửi qua đường bưu điện công cộng (Git). Chỉ đúng cái kho đó (cluster có private key tương ứng) mới mở được hộp.

</Eli5>

## Vì sao DevOps phải giải quyết đúng bài toán này?

Secret lộ trong Git là một trong những sự cố bảo mật phổ biến và tốn kém nhất — vì lịch sử Git gần như không thể "xoá sạch" sau khi đã push. GitOps làm bài toán này khó hơn vì triết lý là "mọi thứ vào Git", nên cần cơ chế rõ ràng để secret là ngoại lệ an toàn.

### External Secrets Operator (ESO)

```yaml title="cluster-secret-store.yaml"
apiVersion: external-secrets.io/v1
kind: ClusterSecretStore
metadata:
  name: aws-secrets-manager
spec:
  provider:
    aws:
      service: SecretsManager
      region: ap-southeast-1
      auth:
        jwt:
          serviceAccountRef:
            name: external-secrets-sa
            namespace: external-secrets
---
apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata:
  name: postgres-auth
  namespace: shop
spec:
  refreshInterval: 1h
  secretStoreRef:
    name: aws-secrets-manager
    kind: ClusterSecretStore
  target:
    name: postgres-auth        # tên Secret Kubernetes được tạo ra
  data:
    - secretKey: POSTGRES_PASSWORD
      remoteRef:
        key: shop/postgres-password
```

`ExternalSecret` **an toàn để commit** — nó chỉ chứa tên secret ở AWS, không chứa giá trị. `ClusterSecretStore` dùng Pod Identity (M13) để `external-secrets-sa` gọi AWS mà không cần access key.

| Ưu điểm | Nhược điểm |
|---|---|
| Secret thật không bao giờ chạm Git | Cần một hệ thống lưu secret bên ngoài (Secrets Manager, Vault…) đang chạy |
| Đổi secret ở nguồn, tự đồng bộ theo `refreshInterval`, không cần commit | Thêm một điểm phụ thuộc/single point of failure (ESO + provider) |
| Audit log tập trung ở AWS CloudTrail | Cluster mới cần cấu hình `SecretStore` + quyền IAM trước khi dùng được |

### Sealed Secrets

```bash
# Trên máy dev, mã hoá secret bằng public key của cluster đích
kubectl create secret generic postgres-auth \
  --from-literal=POSTGRES_PASSWORD='S3cure!' \
  --namespace shop --dry-run=client -o yaml | \
  kubeseal --format yaml > sealed-postgres-auth.yaml
```

```yaml title="sealed-postgres-auth.yaml (an toàn để commit)"
apiVersion: bitnami.com/v1alpha1
kind: SealedSecret
metadata:
  name: postgres-auth
  namespace: shop
spec:
  encryptedData:
    POSTGRES_PASSWORD: AgBy3i4OJSWK+PiTySYZZA9rO43cGDEQ...  # ciphertext, vô nghĩa nếu bị đọc trộm
```

| Ưu điểm | Nhược điểm |
|---|---|
| Không cần hệ thống lưu secret bên ngoài | Mất private key của controller = mất khả năng giải mã MỌI SealedSecret đã tạo |
| Hoạt động ngay cả khi không có kết nối ra ngoài cluster | Đổi secret phải mã hoá lại + commit — không tự đồng bộ như ESO |
| Đơn giản triển khai cho cluster nhỏ | Backup private key là bắt buộc và cực kỳ nhạy cảm |

### Chọn cái nào?

- Đã có **AWS Secrets Manager / HashiCorp Vault** sẵn trong tổ chức, cần xoay vòng (rotate) secret thường xuyên, nhiều cluster dùng chung một secret → **External Secrets Operator**.
- Cluster độc lập, không muốn phụ thuộc dịch vụ ngoài, đội nhỏ → **Sealed Secrets** đơn giản hơn để bắt đầu.
- Có thể dùng **cả hai** cho các loại secret khác nhau trong cùng cluster.

<Callout type="warning" title="Cả hai đều KHÔNG thay thế RBAC">

Secret Kubernetes cuối cùng vẫn chỉ mã hoá base64 (M12) trong etcd — ai có quyền `get secrets` trong namespace đó vẫn đọc được giá trị thật. ESO/Sealed Secrets giải quyết vấn đề "secret trong Git", không giải quyết "ai trong cluster được đọc secret" — đó vẫn là việc của RBAC.

</Callout>

<Callout type="mistake">

**Commit `kubectl create secret --dry-run=client -o yaml` (chưa qua kubeseal/ExternalSecret) vào Git "tạm thời để test".** Đây chính là base64 plaintext — bị commit một lần là coi như đã lộ vĩnh viễn trong lịch sử Git. Luôn đi qua ESO hoặc `kubeseal` trước khi commit bất kỳ file nào có chữ "secret".

</Callout>
