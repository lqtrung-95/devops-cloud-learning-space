<Eli5 title="GitOps là kho hàng có một cuốn sổ chung và một nhân viên luôn túc trực" emoji="📖">

Cách deploy "truyền thống" giống bạn **tự lái xe tải đồ tới kho** mỗi khi có hàng mới (CI chạy `kubectl apply` từ bên ngoài). Xe tải đó phải có **chìa khoá vào kho** — nếu xe tải bị cướp, kẻ cướp có chìa khoá vào thẳng kho của bạn.

**GitOps** thì khác: bạn **không tự vào kho**. Bạn chỉ **viết vào một cuốn sổ chung** (Git repo): "kho nên có đúng những thứ này". Một **nhân viên kho luôn túc trực bên trong** (Argo CD, chạy trong cluster) liên tục đọc sổ và tự sắp xếp hàng cho khớp. Muốn đổi hàng trong kho? Chỉ cần sửa sổ — nhân viên tự làm phần còn lại.

Điểm hay nhất: nếu có ai **lén vào sắp sai đồ** trong kho (`kubectl edit` tay), nhân viên vẫn đọc sổ định kỳ và **tự sắp lại đúng** như sổ ghi — không cần ai phát hiện và sửa tay.

</Eli5>

## Vì sao DevOps chuyển sang GitOps?

Sau M12-M13, bạn đã biết cách deploy bằng `kubectl`/Helm từ máy mình hoặc CI. GitOps giải quyết 3 vấn đề còn lại: **ai đang deploy gì lên prod** (audit qua Git history), **CI có cần quyền truy cập cluster không** (bảo mật), và **drift bị phát hiện thế nào** (một service bị sửa tay lúc nửa đêm rồi quên mất).

<Technical>

### 4 nguyên tắc GitOps (theo OpenGitOps — CNCF)

| Nguyên tắc | Ý nghĩa |
|---|---|
| **Declarative** | Toàn bộ hệ thống được mô tả bằng trạng thái mong muốn (YAML), không phải danh sách lệnh đã chạy |
| **Versioned & Immutable** | Trạng thái mong muốn lưu trong Git — có lịch sử, review qua PR, revert bằng `git revert` |
| **Pulled Automatically** | Một agent phần mềm (Argo CD, Flux) trong cluster tự kéo trạng thái mong muốn về, không ai đẩy từ ngoài vào |
| **Continuously Reconciled** | Agent liên tục so sánh thực tế với Git và tự sửa sai lệch (drift) |

### Push vs Pull — khác nhau ở đâu

```
Push:  Developer → Git → CI (có credentials cluster) → kubectl apply → Cluster
Pull:  Developer → Git ← Argo CD (agent TRONG cluster, tự kéo về) → apply nội bộ
```

| | Push (CI/CD truyền thống) | Pull (GitOps) |
|---|---|---|
| Ai cầm credentials cluster | CI runner (thường external, nhiều pipeline dùng chung) | Chỉ agent nội bộ trong cluster |
| Phát hiện drift | Không — chỉ biết trạng thái lúc pipeline chạy | Có — reconcile liên tục, tự phát hiện lệch |
| Rollback | Chạy lại pipeline cũ hoặc `kubectl apply` tay | `git revert` hoặc rollback trong UI/CLI của agent |
| Bề mặt tấn công | CI bị chiếm quyền = cluster bị chiếm quyền | CI bị chiếm quyền chỉ đẩy được commit (chặn bằng review) |
| Multi-cluster | Pipeline phải biết địa chỉ từng cluster | Mỗi cluster tự kéo Git của mình, không cần "biết" CI |

### Git là nguồn sự thật duy nhất (single source of truth)

Hệ quả quan trọng: **không bao giờ `kubectl apply` tay lên môi trường do GitOps quản lý**. Nếu bạn sửa tay, agent sẽ:

- Với `selfHeal: false` (mặc định một số setup): báo `OutOfSync`, chờ bạn xử lý.
- Với `selfHeal: true`: tự động ghi đè thay đổi tay của bạn về đúng Git trong lần reconcile kế tiếp.

Muốn thay đổi thật sự? Sửa Git, không sửa cluster.

<Callout type="info" title="GitOps không thay thế CI, nó nối tiếp CI">

CI vẫn build, test, push image như bình thường (M05). GitOps chỉ thay đổi **bước cuối cùng**: thay vì CI tự `kubectl apply`, CI chỉ **commit thay đổi cấu hình** (ví dụ image tag mới) vào config repo — bước deploy thật sự do agent trong cluster đảm nhiệm.

</Callout>

<Callout type="mistake">

**Vẫn để CI giữ kubeconfig "phòng khi cần" sau khi chuyển sang GitOps.** Nếu CI vẫn có quyền apply thẳng, bạn chỉ thêm một công cụ (Argo CD) mà không loại bỏ được rủi ro bảo mật cốt lõi — hai đường deploy song song (CI push + Argo CD pull) còn dễ gây xung đột trạng thái hơn.

</Callout>
