<Eli5 title="App repo là công thức nấu ăn, config repo là lịch bếp hôm nay nấu gì" emoji="📋">

**App repo** (`shop-api`) là **công thức nấu ăn**: mã nguồn, Dockerfile, test. Nó gần như không đổi cấu trúc, chỉ đổi nội dung món ăn.

**Config repo** (`shop-config`) là **lịch bếp**: "hôm nay bếp dev nấu món phiên bản nào, bếp staging nấu món nào, bếp khách VIP (prod) nấu món nào". Lịch này đổi liên tục và **mỗi dòng lịch = một quyết định deploy** cần được duyệt.

**Promotion** là quy trình: món nấu thử ở bếp dev ngon → **chép y nguyên công thức đó** (cùng image tag) sang lịch bếp staging → rồi sang lịch bếp khách VIP. Không nấu lại từ đầu ở mỗi bếp — bạn test đúng cái sẽ chạy ở prod, không phải một bản build khác "tương tự".

</Eli5>

## Vì sao DevOps cần tách hai repo này?

Tách app repo khỏi config repo cho phép: đội phát triển và đội vận hành có tốc độ thay đổi khác nhau (code đổi theo sprint, config đổi theo mỗi lần deploy); audit trail rõ ràng ("ai duyệt deploy prod lúc mấy giờ" nằm gọn trong lịch sử PR của 1 repo); và quan trọng nhất — **cùng một artifact đã test được promote nguyên vẹn**, loại bỏ rủi ro "chạy tốt ở staging nhưng prod build khác đi".

### Cấu trúc config repo điển hình

```
shop-config/
├── base/
│   ├── kustomization.yaml
│   ├── deployment.yaml
│   ├── service.yaml
│   └── hpa.yaml
├── overlays/
│   ├── dev/
│   │   ├── kustomization.yaml      # newTag: <commit sha mới nhất>
│   │   └── replica-patch.yaml       # replicas: 1
│   ├── staging/
│   │   ├── kustomization.yaml
│   │   └── replica-patch.yaml       # replicas: 2
│   └── prod/
│       ├── kustomization.yaml
│       └── replica-patch.yaml       # replicas: 5
└── argocd/
    ├── shop-api-dev-application.yaml
    ├── shop-api-staging-application.yaml
    └── shop-api-prod-application.yaml
```

Đây chính là cấu trúc Kustomize base/overlays đã học ở M13 — GitOps chỉ thêm lớp Argo CD Application phía trên để tự sync mỗi overlay.

### App-of-apps — quản lý nhiều Application bằng một Application

Thay vì tạo tay từng Application, dùng một Application "cha" trỏ vào thư mục `argocd/`:

```yaml title="root-application.yaml"
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: shop-apps-root
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/acme/shop-config.git
    targetRevision: main
    path: argocd
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
  syncPolicy:
    automated: { prune: true, selfHeal: true }
```

Thêm một Application mới = thêm một file YAML vào `argocd/` rồi commit — root Application tự tạo nó.

### ApplicationSet — sinh Application hàng loạt theo template

Khi số môi trường/cluster nhiều, viết tay từng Application không mở rộng được. `ApplicationSet` dùng **generator** để sinh tự động:

```yaml title="shop-api-applicationset.yaml"
apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: shop-api
  namespace: argocd
spec:
  generators:
    - list:
        elements:
          - env: dev
            replicas: "1"
          - env: staging
            replicas: "2"
          - env: prod
            replicas: "5"
  template:
    metadata:
      name: "shop-api-{{env}}"
    spec:
      project: default
      source:
        repoURL: https://github.com/acme/shop-config.git
        targetRevision: main
        path: "overlays/{{env}}"
      destination:
        server: https://kubernetes.default.svc
        namespace: "shop-{{env}}"
      syncPolicy:
        automated: { prune: true, selfHeal: true }
```

Generator khác thường dùng: `git` (quét thư mục `overlays/*` tự động, không cần liệt kê tay), `cluster` (một Application cho mỗi cluster đã đăng ký — hữu ích khi có nhiều cluster theo region).

### Promotion — commit là quyết định deploy

Luồng promotion tiêu chuẩn:

1. CI của app repo build, test, push image `shop-api:<sha>`.
2. Bước cuối CI **tự động** commit `overlays/dev/kustomization.yaml` với tag mới (không phải deploy trực tiếp — chỉ ghi vào "lịch bếp dev").
3. Từ dev, tạo PR promote sang staging (nhiều team tự động hoá bước này bằng bot khi dev pass smoke test).
4. Review + merge PR staging → prod tương tự, thường thêm `CODEOWNERS` yêu cầu người có quyền duyệt.

```yaml title=".github/CODEOWNERS (trong config repo)"
/overlays/prod/  @platform-team @tech-lead
```

<Callout type="tip" title="Đừng để CI tự động promote thẳng lên prod">
Auto-sync từ dev lên staging là hợp lý (rủi ro thấp). Nhưng bước staging → prod nên qua PR có người duyệt thật — đây là "gate" quan trọng nhất trong toàn bộ pipeline.
</Callout>

<Callout type="mistake">

**Build image riêng cho từng môi trường (build lại ở bước deploy prod).** Nếu prod build từ source khác dev/staging dù cùng commit, bạn không còn "test đúng cái sẽ chạy" — dependency có thể resolve khác, base image có thể đổi version. Build **một lần**, cùng một image digest chạy qua mọi môi trường.

</Callout>
