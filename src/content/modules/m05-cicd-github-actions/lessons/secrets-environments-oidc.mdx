<Eli5 title="OIDC giống vé vào cổng có ảnh thay cho chìa khoá copy" emoji="🎫">

Cách cũ: bạn **đánh thêm một chìa khoá kho** (AWS access key) rồi **gửi cho anh shipper** (pipeline) giữ luôn. Chìa không bao giờ hết hạn. Anh shipper làm rơi, hay ai đó chụp lại chìa — kẻ gian vào kho lúc nào cũng được, và bạn thậm chí không biết.

Cách mới — **OIDC**: mỗi lần tới kho, shipper xin **công ty chuyển phát (GitHub)** một **vé có ảnh và ghi rõ**: "shipper của đơn hàng `acme/api`, tuyến `main`". **Bảo vệ kho (AWS)** đã thoả thuận trước với công ty: tin vé do công ty ký, nhưng **chỉ cho vào nếu vé ghi đúng tuyến `main`**. Soát xong, bảo vệ đưa **thẻ ra vào tạm, hết hạn sau 1 giờ**.

Không còn chìa khoá nào nằm lâu dài ở đâu để mà lộ.

</Eli5>

### Vì sao DevOps quan tâm?

Access key bị lộ trong repo/log là một trong những nguyên nhân phổ biến dẫn tới sự cố cloud và hoá đơn "đào coin" khổng lồ. OIDC đang dần thành **chuẩn** cho CI/CD kết nối AWS, GCP, Azure — và là câu hỏi phỏng vấn quen thuộc. Kết hợp với **environments** (người duyệt, secret riêng) là bạn có cổng deploy production an toàn.

### Secrets và variables

| Loại | Phạm vi | Dùng cho |
|---|---|---|
| **Repository secret** | Mọi workflow trong repo | Token dịch vụ ngoài (Slack webhook, Sonar) |
| **Environment secret** | Chỉ job khai báo `environment:` đó | Thông tin production — chỉ đọc được sau khi được duyệt |
| **Organization secret** | Nhiều repo được chọn | Secret dùng chung |
| **Variables** (`vars`) | Như trên | Cấu hình **không bí mật**: region, tên cluster |

```yaml
- run: ./scripts/notify.sh
  env:
    SLACK_WEBHOOK: ${{ secrets.SLACK_WEBHOOK }}
    AWS_REGION: ${{ vars.AWS_REGION }}
```

Secret được **che thành `***`** trong log — nhưng chỉ khi in nguyên văn. Base64 hoá rồi in ra là lộ. Secret **không được truyền** cho workflow chạy từ PR của **fork** (trừ `GITHUB_TOKEN` chỉ-đọc).

### Environments: cổng deploy

Settings → Environments → `production`:

- **Required reviewers**: job dừng lại chờ người được chỉ định bấm Approve.
- **Deployment branches and tags**: chỉ `main` (hoặc tag `v*`) được deploy vào môi trường này.
- **Wait timer**, environment secrets/variables riêng.

```yaml
jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: production
      url: https://shop.example.com
    steps:
      - run: echo "Chỉ chạy tới đây sau khi được duyệt"
```

Tính năng environment cho repo private phụ thuộc gói GitHub — kiểm tra tài liệu mới nhất.

### OIDC tới AWS — 3 phần

**1. Đăng ký GitHub là identity provider trong AWS** (một lần mỗi account): URL `https://token.actions.githubusercontent.com`, audience `sts.amazonaws.com`.

**2. IAM role với trust policy khoá chặt repo và nhánh:**

```json title="trust-policy.json"
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:acme/shop-api:ref:refs/heads/main"
        }
      }
    }
  ]
}
```

Khi job dùng `environment: production`, claim `sub` có dạng `repo:acme/shop-api:environment:production` — điều kiện phải khớp đúng dạng đó. Gắn thêm **permission policy** tối thiểu cho role (vd. chỉ push một repo ECR).

**3. Workflow xin token và assume role:**

```yaml title=".github/workflows/deploy.yml"
permissions:
  id-token: write      # bắt buộc để xin OIDC token
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: aws-actions/configure-aws-credentials@v4   # kiểm tra version mới nhất
        with:
          role-to-assume: arn:aws:iam::123456789012:role/gha-deploy
          aws-region: ap-southeast-1
      - run: aws sts get-caller-identity
```

Lưu ý: khai báo `permissions:` ở bất kỳ mức nào sẽ đặt mọi quyền **không liệt kê** về `none` — vì vậy phải ghi lại `contents: read` để checkout được.

### Những điều cấm kỵ

- **`pull_request_target`** chạy với secret và token có quyền ghi của repo gốc. Nếu workflow đó checkout và chạy code từ PR của fork → kẻ lạ chạy code với secret của bạn. Chỉ dùng khi thật hiểu rõ.
- Không đặt **`sub` dạng wildcard rộng** như `repo:acme/*` cho role production.
- Không nối trực tiếp dữ liệu người dùng nhập (tiêu đề PR, tên nhánh) vào `run:` qua `${{ }}` — có thể bị **script injection**. Đưa qua `env:` rồi dùng biến shell.

</Technical>

<Callout type="mistake">

**Tạo IAM user, lưu `AWS_ACCESS_KEY_ID` + `AWS_SECRET_ACCESS_KEY` vào GitHub secrets.** Key sống vĩnh viễn, ai có quyền sửa workflow cũng có thể in nó ra. Chuyển sang OIDC và xoá IAM user đó.

</Callout>

<Callout type="mistake">

**Quên `permissions: id-token: write`.** Lỗi thường gặp: "Credentials could not be loaded" hoặc không lấy được ID token. Không có quyền này, job không xin được vé.

</Callout>

<Callout type="warning">

Trust policy thiếu điều kiện `sub` (chỉ kiểm `aud`) nghĩa là **bất kỳ repo GitHub nào** cũng có thể assume role của bạn. Luôn khoá `sub` theo đúng repo và nhánh/environment.

</Callout>
